## Proposal 1: Terminal-Escape Bypass Patterns
- **Source**: Synthetic — generated from a hand-written seed corpus of known adversarial terminal escape sequences (xterm, VT100, ROP, OSC, CSI variants) plus structural mutations of clean text.
- **Schema**:
  ```
  sample_id:        string   UUID
  input_raw:        string   Original untrusted text (with embedded escapes)
  input_bytes_hex:  string   Hex of UTF-8 byte stream (for multi-byte testing)
  escape_class:     string   One of: c0 | csi | osc | esc | dcs | sos | iso_shift | app_key | utf8_combine | clean
  carrier:          string   Channel: agent_pty | slack_msg | gh_issue_body | pr_diff
  is_benign:        bool     Whether the escape is decorative (color) or adversarial (cursor hijack, title rewrite, screen clear)
  sanitizer_keeps:  string   Output of TerminalSanitizer.sanitize() — ground truth for evaluation
  lost_meaning:     bool     Whether sanitization stripped load-bearing characters
  escapes_through:  int      Count of escape sequences that survived sanitization
  attack_goal:      string   cursor_hijack | screen_clear | title_set | input_echo | osc_exec | none
  ```
- **Why NEXUS cares**: `security/sanitizer.py` is the cross-agent injection front line — every PTY output passes through `TerminalSanitizer.sanitize()` (line 64). The 8 strip patterns (`_C0_STRIP` / `_CSI_STRIP` / `_OSC_STRIP` / `_ESC_STRIP` / `_DCS_STRIP` / `_SOS_STRIP` / `_ISO_SHIFT` / `_APP_KEY_STRIP`) are regex-only and have no benchmark of coverage. Known blind spots: UTF-8 multi-byte combining sequences, 7-bit C1 controls delivered as bare bytes (not ESC-prefixed), OSC payloads split across chunks. A labelled corpus would let us measure recall of the regex set and identify escape classes that slip through.
- **Estimated effort**: M (14–22 h) — requires assembling a seed corpus of ~300 real escape sequences from xterm/VT100/Rxvt specs, then a mutation engine to grow synthetic adversarial variants to ~3,000.
- **First slice**: 300 hand-labelled samples covering the 8 existing escape classes + a `clean` baseline, run through `TerminalSanitizer.sanitize()` to compute per-class recall. Expansion to multi-byte UTF-8 attacks in slice 2.

## Proposal 2: VAP Proof-Chain Tamper Mutations
- **Source**: Synthetic — generated by mutating legitimate VAPRecord instances produced by `VAPProofChain.append()` and feeding them to `VAPProofChain.verify_chain()`.
- **Schema**:
  ```
  mutation_id:        string   UUID
  baseline_record_id: string   ID of the unmodified source VAPRecord
  chain_position:     int      Index in the chain (0 = head)
  tamper_field:       string   Field mutated: actor | action | resource | ctx | outcome | ts | prev_hash | signature | chain_hash
  tamper_kind:        string   bit_flip | byte_swap | truncation | append | null_inject | cross_record_swap
  bytes_changed:      int      Number of bytes altered
  verify_chain_result: bool   Outcome of VAPProofChain.verify_chain() — should be False
  detect_latency_us:  int      Wall-clock time to detect (microseconds)
  adjacent_tampered:  bool     Whether neighbours were also modified (chain-shift detection)
  detected_by:        string   which check fired: prev_hash | signature | chain_hash | none
  ```
- **Why NEXUS cares**: `governor/proof_chain.py:VAPProofChain.verify_chain()` (line 64) is the integrity backbone for IETF VAP 4-layer provenance. The chain is hash-linked via SHA-256 but there is no adversarial test of mutation kinds beyond simple field flips. A mutation benchmark would expose whether `verify_chain()` catches (a) same-field bit-flips where the hash recomputes inconsistently, (b) cross-record `prev_hash` swaps that preserve local hashes, (c) signature-truncation attacks on `record.signature`. Without this, "verify_chain passed" is a load-bearing claim with no falsification data behind it.
- **Estimated effort**: S (6–10 h) — `append()` is deterministic on the inputs it receives, so a mutation harness can be built around an in-process chain of ~50 records and iterate through the 7 tamper kinds × 9 fields = 63 mutation cells.
- **First slice**: 200 mutated records across the 7 tamper kinds, with `chain_position=0` and a 3-record baseline chain. Goal: assert `verify_chain()` returns False for every mutation, then expand to longer chains in slice 2 to test cross-record swap detection.

## Proposal 3: KAIJU 4-Variable Authorization Decision Cases
- **Source**: Synthetic — generated by enumerating the cartesian product of `ScopeLevel` × `ImpactLevel` × `ClearanceLevel` × `IntentKind` and labelling the expected decision against the 4-variable gate logic in `kaiju_auth.py`.
- **Schema**:
  ```
  case_id:        string   UUID
  agent_id:       string   Synthetic agent identifier
  scope:          string   ScopeLevel: self | project | global
  impact:         string   ImpactLevel: low | medium | high | critical
  intent:         string   IntentKind: read | write | execute | delete | deploy | unknown
  clearance:      string   ClearanceLevel: reader | contributor | admin
  decision_actual: string  KaijuAuthorizer.authorize() output: allow | deny | hold | halt
  expected_decision: string Human-labelled expected outcome for the (scope, impact, intent, clearance) tuple
  held_in_queue:  bool     Whether the case was added to the HOLD queue
  review_required: bool   Whether human review was flagged
  risk_flags:     list     Risk flags raised (e.g. "scope_mismatch", "intent_ambiguous")
  policy_version: string   Version of constitution.yaml active at evaluation time
  ```
- **Why NEXUS cares**: `governor/kaiju_auth.py` defines the 4-variable gate (Scope × Impact × Intent × Clearance) and is the first call inside `NexusGovernor.check_access()` (`governor/base.py`). HOLD is a critical non-terminal state — cases that hit HOLD enter a review queue and must be resolved by a human or escalated agent. The transition rules between ALLOW / DENY / HOLD / HALT are scattered across `KaijuAuthorizer.authorize()` and have no combinatorial test. A labelled decision dataset would (a) verify the hold-queue never silently promotes to ALLOW, (b) detect degenerate cells where the same input always returns the same decision regardless of policy_version, (c) give compliance.py a regression target for IETF VAP-aligned audit requirements.
- **Estimated effort**: M (12–18 h) — the 4 enums have ~6 × 4 × 6 × 3 ≈ 432 raw tuples; after collapsing equivalent cells and labelling 1,000–1,500 representative cases with expected decisions. Needs a labelling pass against the actual code in `kaiju_auth.py` to avoid synthesising decisions the implementation does not produce.
- **First slice**: 200 cases covering all `clearance=admin` cells (lowest expected ambiguity, fastest to label) plus the 30 high-risk combinations of `(impact=critical) × (intent ∈ {delete, deploy, unknown}) × (clearance ∈ {reader, contributor})` that should always produce DENY or HALT.

## Trade-offs to flag for speci
- **Terminal-Escape Bypass**: A `clean` baseline corpus is easy to fabricate; an adversarial corpus is harder — needs to draw from a known-bad reference (e.g. xterm CVE writeups) to avoid inventing vectors that don't exist in the wild. Decision on seed-corpus sourcing belongs to the security owner.
- **VAP Tamper Mutations**: The chain uses `hashlib.sha256` over `json.dumps(..., default=str)` — generator must match this exact serialization or mutation detection rates will be misleading. Confirming this serialization contract is out of scope; should reference `proof_chain.py:_record_signature` (line 78) as ground truth.
- **KAIJU Authorization Cases**: The 4-variable gate is policy-driven (`constitution.yaml`); any new policy version would invalidate the labelled expected_decision column. The dataset must either pin a `policy_version` per row (planned) or be regenerated on each policy bump — that regeneration cadence is a decision the governance owner should make.
