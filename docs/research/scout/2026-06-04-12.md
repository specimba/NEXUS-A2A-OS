## Findings (NEXUS-relevant only)

### 1. HaluNet — Multi-Granular Internal-Signal Hallucination Risk Estimator for LLM QA (arXiv:2512.24562)
- Source: https://arxiv.org/abs/2512.24562
- Why NEXUS cares: HaluNet is a lightweight neural detector that fuses three internal-signal classes — token log-likelihood, predictive entropy, and hidden-state embeddings — into an answer-level hallucination risk score, trained with LLM-as-a-Judge weak supervision. It achieves 0.874 AUROC / 0.869 AUPRC on a 300-example human eval (SQuAD / TriviaQA / Natural Questions), with the top-20% highest-risk answers containing 96.5% of errors (2.06× lift over base error rate). Critically, HaluNet runs from a single generation pass — no external judge, no multi-sampling — so it is latency-compatible with NEXUS's inline trust scoring. NEXUS's `src/nexus_os/monitoring/trust_scorer.py` currently scores policy compliance but does not consume the model's own internal generative signals; adding a HaluNet-style branch that reads entropy + hidden-state at answer boundaries would let `src/nexus_os/governor/trust_kernel.py` (CDR-stage Detect) flag high-risk outputs *before* they reach `compliance.py` policy evaluation. The signal-fusion pattern (likelihood × entropy × hidden-state) also generalizes: NEXUS's `src/nexus_os/vault/memory_adapter.py` could use the same three-signal recipe to score memory write risk (a write whose hidden state, entropy, and likelihood all disagree with prior successful writes is suspect).
- Suggested follow-up: Prototype a `HaluNetBranch` in `src/nexus_os/monitoring/trust_scorer.py` that consumes (a) per-token log-likelihood deltas, (b) rolling predictive entropy, and (c) last-layer hidden-state embeddings from the active ModelRelay response. Emit `hallucination-risk-score` to `src/nexus_os/observability/` whenever the score crosses a configurable threshold, and gate high-impact tool calls in `src/nexus_os/governor/kaiju_auth.py` on the score. Calibrate the threshold against the model_arena golden set to avoid false-positive hold-queue saturation.

### 2. Lagrange Labs DeepProve Open-Source — Production-Grade zkML for End-to-End LLM Inference (2026-06-04)
- Source: https://www.marketminute.com/article/getnews-2026-6-4-lagrange-labs-open-sources-deepprove-the-first-production-grade-zkml-system-to-generate-over-12-million-cryptographic-ai-proofs (mirror: https://eprint.iacr.org/2026/1112)
- Why NEXUS cares: DeepProve is the first production-grade zkML system to ship with native ONNX, safetensors, and GGUF support, covering the exact model formats NEXUS's ModelRelay v6 already routes (HuggingFace / NVIDIA NIM / OpenRouter :free). Performance is non-trivial: 60× faster LLM proofs and 671× faster verification than prior state of the art, with 12M+ proofs generated and 3M+ verified in production over the past year. For NEXUS this lands in two places. First, `src/nexus_os/governor/proof_chain.py` (VAP chain) currently produces tamper-evident audit trails via signed event chains; integrating zkML proofs at chain anchors would let external auditors verify that a specific ModelRelay response was produced by a specific model version, on a specific input, without trusting the Zo host — addressing a class of "did this agent actually use the model it claims?" dispute that pure VAP chains cannot resolve. Second, `src/nexus_os/observability/` could expose a `nexus.proof.verify` MCP tool that accepts a DeepProve receipt + claim and returns "valid" / "invalid" / "stale model version" — letting third-party agents in the OpenClaw swarm cryptographically verify NEXUS-produced outputs before treating them as inputs.
- Suggested follow-up: Add a thin `src/nexus_os/governor/zkml_proof.py` adapter that wraps DeepProve's prover/verifier API, keyed by ModelRelay's `models.json` model IDs so each model version gets a unique prover key. Emit a `zkml-proof-attached` event on the VAP chain whenever a high-impact or high-trust-score inference completes; the existing `proof_chain.py` already has the event-shape contract. Add a test that proves a deterministic prompt and verifies the resulting receipt against the public dashboard at deep-prove.lagrange.dev to confirm the integration round-trips.

### 3. CostGuard + AgentBrake — Two Independent Pre-Execution Circuit Breakers for LLM Tool Calls
- Source: https://dev.to/nilofer_tweets/costguard-a-real-time-circuit-breaker-that-stops-ai-spend-before-it-gets-out-of-control-48oe (CostGuard); https://dev.to/bossmetallique/i-built-a-circuit-breaker-for-llm-agents-after-seeing-someone-lose-200-overnight-21ba (AgentBrake)
- Why NEXUS cares: NEXUS's `src/nexus_os/monitoring/token_policy.py` enforces post-hoc rate limits (per-agent, per-lane, per-day) but has no pre-execution breaker — a single runaway agent can still consume its full budget before any cap fires. Two independent open-source designs landed this week that solve the gap differently, and both are architecturally compatible with NEXUS. CostGuard is a local FastAPI proxy sitting in front of providers with four-tier hard limits (per-session / per-hour / per-day / per-project) and a "safe mode" requiring explicit confirmation above a configurable spend threshold. AgentBrake is a Python decorator that intercepts tool calls and runs three checks before execution: Loop (same tool+args repeated), Budget (cost cap), Escalation (tool allowed). The interesting design difference: CostGuard enforces at the *transport layer* (catches spend regardless of agent framework), while AgentBrake enforces at the *function call layer* (catches loops/duplicates but not malformed prompts). For NEXUS, `src/nexus_os/relay/model_relay.py` is already a transport-layer proxy, so CostGuard's per-tier hard limits could be added in ~50 lines as a pre-call cost estimation + decision. AgentBrake's Loop/Esc detection could be added to `src/nexus_os/mcp/functiongemma_router.py` because the router already sees every tool call — checking the last N tool calls for a "same tool + same args" pattern is O(1) memory. Both are fail-closed by design, which is consistent with NEXUS's `src/nexus_os/governor/trust_kernel.py` CDR-stage philosophy.
- Suggested follow-up: Add a `pre_call_cost_estimate` step in `src/nexus_os/relay/model_relay.py` that runs tiktoken-based cost estimation against `models.json` pricing and blocks (HTTP 429) when any of the four CostGuard tiers is exceeded. Add a `loop_detector` ring buffer in `src/nexus_os/mcp/functiongemma_router.py` keyed on `(tool_name, args_hash)` that triggers a Kaiju hold-queue review if the same fingerprint appears ≥3 times in the last 10 calls. Both should be observability-tagged with `nexus.monitoring.breaker` labels so Loki queries can correlate breaker trips with `token_policy` and `trust_kernel` events.

### 4. PARALLAX — Benchmark Confounds That Inflate Hallucination-Detector AUROC (arXiv:2605.17028)
- Source: https://arxiv.org/html/2605.17028
- Why NEXUS cares: PARALLAX is the first systematic study showing that high AUROC claims for internal-signal hallucination detectors are partially an artifact of benchmark construction. Two confounds: (1) teacher-forced prompts (which embed ground-truth in the input) inflate AUROC to 0.85–1.00 for artifact-exploiting methods like TxTemb, but the gains vanish on live-generation corpora; (2) narrow cross-model / cross-benchmark evaluation overfits detectors to specific model artifacts. On RAGTruth, both supervised and unsupervised methods cluster at AUROC 0.43–0.57 — barely above chance. This is directly relevant to NEXUS's planned `HaluNetBranch` (finding #1) and the existing `src/nexus_os/model_arena/mini_arena.py` evidence-collection layer. If NEXUS adopts internal-signal hallucination detection, it must evaluate on *live-generation* corpora with post-hoc human labels, not teacher-forced benchmarks. PARALLAX also recommends cross-benchmark / cross-model validation as a reporting requirement — which NEXUS's mini_arena should adopt as a gate before any detector is promoted into the trust kernel.
- Suggested follow-up: Add a "PARALLAX check" to `src/nexus_os/model_arena/mini_arena.py`: any new hallucination detector submitted to the arena must report AUROC on (a) teacher-forced prompts, (b) live-generation prompts, and (c) RAGTruth. Live-generation AUROC must be within 0.15 of teacher-forced AUROC; otherwise the detector is flagged "artifact-dependent" and rejected. This is a report-only evaluator; it does not change trust_kernel behavior, but it prevents promoting detectors whose high scores are a benchmark artifact.
