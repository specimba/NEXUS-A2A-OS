### 1. OWASP Enterprise Adoption Maturity Model — Two-Axis (Adoption AT0–AT5 × Governance L0–L3) Matrix with "Red Cell" Warning for Under-Governed Deployments
- Source: https://www.infosecurity-magazine.com/news/owasp-agentic-ai-security-maturity/ (2026-06-05); primary paper: https://genai.owasp.org/resource/state-of-agentic-ai-security-and-governance/ (published 2026-06-03, presented by Ariel Fogel at OWASP GenAI Security Summit @ Infosecurity Europe 2026 on 2026-06-04)
- Why NEXUS cares: OWASP's first industry-standard maturity model for agentic AI collapses the entire governance question into a 2-axis decision matrix: where does the agent sit on adoption (AT0 Shadow AI → AT5 Custom in-house agent, six levels), and where does governance sit (L0 Unaware/ad-hoc → L3 Integrated continuous oversight, four levels). The "red cell" rule — never operate in cells where adoption tier exceeds governance level — is the most actionable sentence in the report, and it maps directly onto NEXUS's existing safety layer. NEXUS's `src/nexus_os/governor/kaiju_auth.py` is the L2–L3 governance primitive; the FunctionGemma router in `src/nexus_os/mcp/functiongemma_router.py` is the L2 primitive; the CDR-stage trust kernel in `src/nexus_os/governor/trust_kernel.py` is L3. What NEXUS does not yet have is a single `nexus.governance.maturity.cell` derived state object that places every running agent in (AT, L) coordinates and alerts when the cell is red. The OWASP operational logic — "invest in controls specifically designed for agentic systems or reduce the agent's permissions and autonomy until existing controls suffice" — also gives NEXUS a vocabulary for `kaiju_auth.py` deny-with-demotion responses: instead of "deny," the hold-queue response can now say "demote AT tier until governance catches up." Fogel also flags four runtime primitives that OWASP expects at L3: live behavioral baselines, real-time containment and stop mechanisms, joined safety/security incident response, and identity hygiene (ephemeral credentials + cryptographic attestation) — all four of which are partially present in NEXUS but not yet packaged as a single L3-compliance claim.
- Suggested follow-up: Add a `maturity_cell` derived state to `src/nexus_os/governor/kaiju_auth.py` that computes `(AT_tier, L_level)` for every agent at startup and after every significant scope change, sourced from (a) `AT_tier` = the agent's profile tag (set by NEXUS deployer config: AT3 for low-code citizen, AT4 for code-executing, AT5 for in-house NexusGovernanceMCP agents); (b) `L_level` = the live state of the agent's governance instrumentation (L0 if no sanitizer/Loki/policy, L1 if policy-only, L2 if HITL + SBOM + periodic monitoring, L3 if real-time dashboards + kill switch + governance-as-code). Emit a `nexus.maturity.cell_red` event to `src/nexus_os/observability/audit_log.py` when `AT_tier > L_level` and surface a `nexus.maturity.coordinates` Loki label so the dashboard can plot all agents in (AT, L) space — this is the single most distinctive NEXUS marketing surface relative to the OWASP framework. Add a `demotion_hint` to Kaiju hold-queue responses: when denial happens, the deny reason string now includes the suggested `demote_to(AT_target)` so an operator who can't immediately raise the L level knows the exact scope reduction needed to move the agent out of the red cell. Cross-reference the OWASP-required L3 primitives against NEXUS: (1) live behavioral baselines → extend `src/nexus_os/monitoring/trust_scorer.py` with a per-agent baseline; (2) real-time containment → already present in `src/nexus_os/security/sanitizer.py` + `kaiju_auth.py` hold queue; (3) joined safety/security incident response → new doc at `docs/governance/incident-join.md` mapping NEXUS safety events to security events; (4) identity hygiene / ephemeral credentials → new doc at `docs/governance/ephemeral-credentials.md` defining the per-tool-call token lifecycle that the Mitiga Claude Code finding (#2) makes urgent.

### 2. Mitiga Claude Code MCP-Token-Theft Chain — `~/.claude.json` Rewrite via Malicious npm Post-Install Hook, Anthropic Declined to Patch
- Source: https://www.csoonline.com/article/4181230/claude-code-has-an-mcp-security-problem-and-your-developers-are-already-using-it.html (2026-06-05); primary: https://www.mitiga.io/blog/claude-code-mcp-token-theft-mitm; cross-confirmed https://www.securityweek.com/claude-code-oauth-tokens-can-be-stolen-through-stealthy-mcp-hijacking/
- Why NEXUS cares: Mitiga's disclosure describes a *live, unpatched* attack on Anthropic's Claude Code that is the MCP-equivalent of a session-hijack: a malicious npm package with a post-install hook silently rewrites `~/.claude.json` to redirect MCP server endpoints to attacker-controlled infrastructure; the OAuth tokens the developer previously stored in the same file then leak in transit as Claude Code's authenticated requests route through the attacker. Anthropic's response (declined to patch on 2026-04-12, reasoning "user consented to install the package") leaves the attack chain open as of the CSO Online writeup on 2026-06-05. Three things make this NEXUS-relevant. First, the OpenClaw gateway in the NEXUS mesh runs MCP servers with the same OAuth-storage pattern (see `src/nexus_os/mcp/server.py` and the `mcpTrustVerifier` from 2026-05-31-00). The Mitiga finding is a *config-file* attack — the routing layer is a file the agent reads at startup, and the file is the trust boundary. NEXUS's `src/nexus_os/security/sanitizer.py` should be extended to monitor config-file drift on agent startup (and on every MCP handshake) the same way it monitors prompt content. Second, the attack is *silent on the SaaS side*: the request reaches Jira/Confluence/GitHub with a valid bearer token, the user-agent and egress IP look right (Anthropic's egress range), and the audit logs show a "valid" request. The only signal is the request was never initiated by the developer. This is the *exact* failure mode that NEXUS's VAP chain in `src/nexus_os/governor/proof_chain.py` is designed to detect — a VAP event carries the originating `parent_call_id` of the user's intent, and a request that arrives with a valid token but no `parent_call_id` ancestor is suspicious. Today NEXUS's VAP chain is internal to NEXUS; it does not extend to outbound MCP calls. Third, Mitiga's three recommended detections — monitor `~/.claude.json` for unexpected changes, treat npm post-install hooks as first-class supply-chain risk, rotate OAuth tokens after any suspected incident — are operational primitives NEXUS should expose as a `nexus.mcp.config_audit` MCP tool that an external security team (or a CI scan) can call against a NEXUS-equipped fleet.
- Suggested follow-up: Add a `ConfigFileWatchdog` helper to `src/nexus_os/security/sanitizer.py` that snapshots `~/.claude.json`, `~/.cursor/`, and the NEXUS agent's own config file at startup and re-checks the hash on every MCP handshake; emit a `nexus.config.drift` event when the hash changes and auto-quarantine the agent until a human re-approves the change via the Kaiju hold queue. Wire the VAP chain in `src/nexus_os/governor/proof_chain.py` to require every outbound MCP request to carry a `parent_intent_id` from the originating user turn; reject any outbound MCP request whose token is valid but whose `parent_intent_id` is missing or stale (>60s), and emit a `nexus.vap.orphan_request` event. Add a `nexus.mcp.config_audit` MCP tool to `src/nexus_os/mcp/server.py` that returns the current `~/.claude.json` hash, the last 10 changes, and the list of MCP server endpoints currently registered — this makes the Mitiga attack detectable by a NEXUS-equipped security team's automated scan. Document the post-install-hook threat in `docs/security/npm-hooks.md` and add a CI check that fails if any new dependency in `NEXUS-OS/` or `Skills/*/scripts/` declares a post-install hook in its `package.json` without an explicit `// nexus-approved: <reason>` comment. The OWASP "ephemeral credentials" primitive from finding #1 also lands here: switch NEXUS's MCP token storage from long-lived OAuth refresh tokens to short-lived (5-minute) bearer tokens issued by a token-rotation sidecar, so even a config-rewrite attack has a tight blast radius.

### 3. Willow (formerly Webrix) — $7M Seed IAM Layer for AI Agents with Okta/Entra Integration, Shadow-AI Discovery, 100+ Connector Marketplace
- Source: https://www.securityweek.com/willow-raises-7-million-for-securing-autonomous-ai-agents/ (2026-06-05); cross-confirmed https://fintech.global/2026/06/05/hetz-ventures-backs-willows-7m-ai-agent-security-play/ and https://cryptobriefing.com/willow-raises-7m-secure-ai-agents/
- Why NEXUS cares: Willow ships in stealth-and-public-lite form the *exact* pattern NEXUS has been building piecemeal across `src/nexus_os/governor/kaiju_auth.py`, `src/nexus_os/security/sanitizer.py`, and the OpenClaw gateway on port 18789 — but Willow wraps it as a turnkey product with five primitives NEXUS does not yet have. (a) **Per-agent IdP identity** — Willow assigns each AI agent (Claude, Gemini, ChatGPT, Codex, Cursor, n8n, custom) a verifiable identity via Okta/Entra so the agent's actions are attributable to a specific non-human principal, not the human user. NEXUS's `src/nexus_os/governor/kaiju_auth.py` is per-call, not per-agent; the agent identity is implicit in the SDK session. (b) **Runtime least-privilege enforcement** — Willow checks every agent tool call against an IdP-derived policy at call time, returning 403 on violation. NEXUS does this in `kaiju_auth.py` but the policy source is local config; Willow makes the IdP the source of truth, which means a workforce offboarding in Okta/Entra propagates instantly to agent permissions. (c) **Shadow-AI discovery** — Willow enumerates agents the org is not paying for (a developer running personal Claude Code against corp Jira) and flags them. NEXUS's `src/nexus_os/mcp/functiongemma_router.py` could surface a similar view by sampling the inbound traffic at the gateway; today it doesn't. (d) **Audit trail routed through Slack/Teams** — Willow sends every allow/deny decision to a Slack/Teams channel with the agent identity, action, and IdP policy version. NEXUS has Loki labels but no native Slack decision-routing. (e) **Self-hosted/air-gapped deploy** — Willow supports SaaS, dedicated cloud, *and* self-hosted (including air-gapped), which is the deployment shape NEXUS's `Kilocode` provider class and `OpenClaw` gateway already use. Willow is a useful *validation* of the NEXUS architecture (the market is moving toward "agent IAM" as a category) and a useful *competitive benchmark* — NEXUS is more opinionated (Python governance API, OpenClaw-mesh-native, governance-as-code in `compliance.py`) but Willow is more turnkey for a non-NEXUS customer. The relevant question for NEXUS is not "build like Willow" but "make the NEXUS IdP-integration primitive first-class so a NEXUS-equipped fleet can use Okta/Entra as the policy source of truth."
- Suggested follow-up: Add an `idp_integration` config block to `src/nexus_os/governor/kaiju_auth.py` that accepts Okta/Entra/Google Workspace API endpoints and resolves `agent_id` → `principal_id` → `group_membership` at every KaijuAuth call; cache the resolution for 60s with a Redis-backed invalidation on workforce change events. Add a `nexus.shadow_ai.discovery` MCP tool to `src/nexus_os/mcp/server.py` that scans the gateway's inbound traffic for agent SDK signatures and returns a list of (agent_sdk, first_seen, last_seen, est_calls_per_day, auth_status) tuples; the output is the Willow "shadow AI" view, NEXUS-native. Extend `src/nexus_os/monitoring/audit_log.py` to emit a `nexus.decision.slack_routed` event for every allow/deny that the operator's Slack/Teams workspace is configured to receive, with a `slack_channel_id` label. Document the IdP integration in `docs/governance/idp-integration.md` and add a `tests/governance/test_idp_policy.py` that points Kaiju at a mock Okta endpoint, offboards a principal, and asserts the agent's tool calls begin denying within the 60s cache TTL. Track Willow's connector marketplace and skills/plugins catalog in `docs/competitive/willow-2026.md`; if Willow ships an open-source "agent IAM SDK" within the next 6 months, evaluate adopting it as the policy-decision-point front-end for `kaiju_auth.py`.

### 4. JustAskJacky AI-Malware Campaign — Microsoft DART's First Disclosed Real-World Backdoor Disguised as a Legitimate AI Assistant
- Source: https://www.infosecurity-magazine.com/news/attackers-ai-adoption-malware/ (2026-06-04); Microsoft DART presentation at Infosecurity Europe 2026-06-03 ("Securing AI in the Age of Intelligent Threats")
- Why NEXUS cares: JustAskJacky is the first publicly disclosed malware campaign by a named threat actor that **disguises its backdoor as a legitimate AI assistant installer** — a Java-based backdoor with valid digital signatures, a professional-looking UI, and a persistence mechanism (scheduled task every 4 hours) that keeps the agent reachable for telemetry and re-tasking. The campaign matters to NEXUS in two ways. First, the *threat model* is now in scope for `src/nexus_os/security/sanitizer.py`: an "AI assistant" on a developer or operator's machine is not necessarily the model the operator thinks it is. NEXUS's `src/nexus_os/mcp/functiongemma_router.py` already classifies inbound MCP server connections by intent; extending that classification to *the agent process itself* — fingerprinting the runtime, the UI, the network egress pattern, and the persistence mechanism — is a small, additive change that catches the JustAskJacky shape. The persistence-mechanism fingerprint (4-hour scheduled task, Java backend) is exactly the kind of behavioral signal that NEXUS's Loki labels could surface as a `nexus.runtime.anomaly` event. Second, Microsoft DART's accompanying statistic — "nearly half of AI code contains flaws that attackers can exploit" — is a useful baseline for `src/nexus_os/model_arena/mini_arena.py`. The arena could publish a "code-flaws-in-AI-suggested-fixes" eval that measures the rate of exploitable flaws in unprompted AI-generated code, then measure the same rate on NEXUS-prompted code (with the safety layer instructing the model to prefer safe idioms). The deltas are a marketing-grade signal that NEXUS is the safer default.
- Suggested follow-up: Add a `RuntimeFingerprint` helper to `src/nexus_os/security/sanitizer.py` that snapshots (a) process tree, (b) installed scheduled tasks, (c) outbound DNS lookups, (d) loaded DLLs / .so files, (e) any unsigned or anomalously-signed Java/Python runtimes, on every agent startup and at 5-minute intervals thereafter; emit a `nexus.runtime.fingerprint.changed` event when the fingerprint drifts, and a `nexus.runtime.persistence.detected` event when a new scheduled task is created at runtime. Cross-reference the fingerprint with a known-malicious-runtime allowlist (JustAskJacky's specific Java launcher hashes, WormGPT's known Python packaging, etc.) and auto-quarantine any matching agent via the Kaiju hold queue. Add a `code_flaws_per_kLOC` eval to `src/nexus_os/model_arena/mini_arena.py` that runs a 100-prompt coding battery through NEXUS-prompted and unprompted models, then runs a static analyzer (semgrep or CodeQL ruleset) over the output; publish the rate per model + the NEXUS-prompted delta. The eval should specifically target the JustAskJacky pattern: persistence mechanisms created by AI-suggested fixes, hardcoded credentials, eval-based code, and Java/Python launchers. Add a Loki dashboard panel `JustAskJacky indicator score` that shows the fleet-wide count of agents with the JustAskJacky runtime fingerprint over time.
