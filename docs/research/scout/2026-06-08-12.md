### 1. Flowise CVE-2026-40933 (Obsidian Security, 1 Jun 2026) + PoC Against the Vendor Patch — The Third 2026 RCE in an MCP-Adjacent Builder (After Langflow CVE-2026-33017 and Langflow CVE-2025-3248), the First Instance Where the Vendor Patch Has Been *Publicly Demonstrated Bypassable*, and a Direct Path to Add a `nexus.mcp.transport=stdio` Allowlist-Override Guard to `src/nexus_os/security/sanitizer.py` So a NEXUS-Equipped MCP Server Refuses stdio Transport by Default and Requires an Explicit `--allow-stdio` Flag to Enable It
- Source: Infosecurity Magazine "Critical Flowise Flaw Gives Attackers Full Server Control" https://www.infosecurity-magazine.com/news/flowise-mcp-rce-poc/ (1 Jun 2026, Obsidian Security research); Obsidian Security "When is stdio MCP actually a vulnerability" https://www.obsidiansecurity.com/blog/when-is-stdio-mcp-actually-a-vulnerability (1 Jun 2026, primary writeup with PoC); CVSS critical; Flowise 52,000+ GitHub stars; self-hosted deployments vulnerable by default, managed Flowise Cloud unaffected
- Why NEXUS cares: Flowise CVE-2026-40933 is the *third* 2026 RCE in an MCP-adjacent builder (after Langflow CVE-2026-33017 and the earlier Langflow CVE-2025-3248), and all three share the same architectural class: **the Custom MCP tool with stdio transport launches a user-supplied command as an unsandboxed child process on the agent host, and the builder lets users export/import chatflows so an attacker can hide a malicious command inside a chatflow that fires on import with no save/run/approval step**. The NEXUS-relevant datum is the *transport-level* fix Obsidian Security recommends: **disable stdio transport entirely in favor of Server-Sent Events (SSE)**, because input-validation allowlists can be expressed around by an attacker still inside the allowed input. The vendor's published input-validation patch was *publicly bypassed* by the PoC, so defense-in-depth at the *transport* layer is the only mitigation that holds. Three concrete NEXUS maps. **(a) Transport-level stdio kill-switch ↔ NEXUS's `src/nexus_os/mcp/server.py` NexusGovernanceMCP** — NEXUS's `NexusGovernanceMCP` should default to *refusing* stdio transport and require an explicit `--allow-stdio` flag (or `nexus.mcp.allow_stdio=true` in `models.json`) to enable it; this is a class-level mitigation, not a bug-level one, and the Flowise CVE-2026-40933 PoC-against-patch is the first time a vendor patch has been publicly demonstrated bypassable, so a NEXUS-issued MCP server should not trust vendor patches for stdio transport and should *kill the transport by default*. **(b) Chatflow-as-code RCE-on-import ↔ NEXUS's `src/nexus_os/security/sanitizer.py` `ConfigFileWatchdog` and the new `NexusOwaspClassDetector` from 2026-06-08-00 #1** — the chatflow-as-code RCE-on-import is the same class as the dependency-prose injection class from 2026-06-08-00 #2 (a "trusted" content artifact auto-executes on load), so the existing `ConfigFileWatchdog` baseline-snapshot pattern should be extended to cover chatflow files (`*.chatflow.json`, `*.flow.json`, `*.workflow.json`) so a NEXUS-equipped agent refuses to import a chatflow that has not been previously snapshotted. **(c) Patch-bypass disclosure ↔ NEXUS's `src/nexus_os/governor/proof_chain.py` and the existing VAP chain** — when a vendor patch is publicly bypassed, NEXUS should auto-elevate the CVE-class in `owasp_llm_patterns.json` to "patch-bypass" status and emit a `nexus.owasp.llm01_class_detected{class=flowise_stdio_chatflow,cve_family=CVE-2026-40933,patch_bypass=true}` Loki event so downstream jobs can quarantine any host running the affected vendor version. The pattern is *vendor version ∈ known_patched_set AND CVE-class ∈ owasp_llm_patterns.json AND patch_bypass=true*.
- Suggested follow-up: Add a `nexus.mcp.transport=stdio|sse` default to `src/nexus_os/mcp/server.py` that defaults to `sse` and refuses `stdio` unless the operator sets `--allow-stdio` on the command line OR `nexus.mcp.allow_stdio=true` in `models.json`; the refusal is logged as a `nexus.mcp.transport_refused{requested=stdio,reason=flowise_cve_2026_40933_class}` Loki event and a `nexus.mcp.stdio_enabled=true` gauge flips to false so the dashboard can render the per-deployment stdio exposure. Extend `src/nexus_os/security/owasp_llm_patterns.json` (per 2026-06-08-00 #1) with three new class signatures: (1) Flowise stdio chatflow RCE class — `(tool_call_targets exec OR child_process.spawn AND (transport=stdio) AND (process_ancestor matches flowise|langflow|chatflow-import))`, (2) patch-bypass class — `(vendor_version ∈ known_patched_set) AND (cve_class ∈ owasp_llm_patterns.json) AND (patch_bypass=true)`, (3) chatflow-as-code RCE-on-import class — `(imported_file matches *.chatflow.json|*.flow.json|*.workflow.json) AND (imported_file contains tool_call_definition) AND (import_source not in pinned_allowlist)`. Add a `ChatflowWatchdog` to `src/nexus_os/security/sanitizer.py` that extends the existing `ConfigFileWatchdog` baseline-snapshot pattern to cover chatflow / flow / workflow files (snapshots SHA-256 of file contents, refuses import of any file not previously snapshotted, mirrors MCPSense v0.3.0's `--update-baseline` UX from 2026-06-08-00 #2). Wire the new pattern signatures into the existing `NexusOwaspClassDetector` from 2026-06-08-00 #1 so a match emits `nexus.owasp.llm01_class_detected{class=flowise_stdio_chatflow|patch_bypass|chatflow_as_code,cve_family=CVE-2026-40933|...}` with the inbound tool call ID, the vendor version, the `retrieve_then_call` dataflow, and a `patch_bypass=true` label when applicable. Add a `PatchBypassWatchdog` to `src/nexus_os/governor/proof_chain.py` that, on every NEXUS startup, pulls the `cve_bypass_feed` (a versioned JSON file at `src/nexus_os/security/cve_bypass_feed.json` that lists vendor CVEs whose official patch has been publicly bypassed, starting with CVE-2026-40933) and auto-elevates any host running an affected vendor version to a "patch-bypass-vulnerable" VAP state that requires human review before any tool call on the affected class. Add `tests/security/test_flowise_stdio_chatflow.py`, `tests/security/test_patch_bypass_detector.py`, and `tests/security/test_chatflow_watchdog.py` covering (a) stdio refusal with no `--allow-stdio`, (b) stdio acceptance with `--allow-stdio` and a `nexus.mcp.allow_stdio=true` config, (c) chatflow import refusal for un-snapshotted file, (d) `NexusOwaspClassDetector` matching the three new class signatures, (e) `PatchBypassWatchdog` auto-elevating a host running Flowise < 3.x.y to a "patch-bypass-vulnerable" VAP state, (f) `ChatflowWatchdog` SHA-256 baseline snapshot creation, update with `--update-baseline`, and refusal on subsequent mismatch.

### 2. OWASP Agentic Research Council (Infosecurity Europe, 1 Jun 2026) + Dark Reading HITL A2A Chain Governance (June 2026) — The First Time OWASP Has Institutionalized a Continuous Working Group (Not a Yearly Top 10) for the Agentic Threat Class, and the First Enterprise-Press Framing of Risk-Based Approvals Across A2A Action Chains as a Distinct Governance Pattern, Both of Which Map Onto NEXUS's `src/nexus_os/governor/` Module Set With Concrete Schema and Contain-Stage Wiring
- Source: Infosecurity Magazine "Infosecurity Europe: OWASP Forms New Agentic Research Council" https://www.infosecurity-magazine.com/news/owasp-new-agentic-research-council/ (1 Jun 2026, council chartered at Infosecurity Europe London); Dark Reading "Human-in-the-Loop (HITL): Balancing AI Speed with Human Oversight" https://www.darkreading.com/identity-access-management-security/human-in-the-loop-hitl-balancing-al-speed-with-human (June 2026, risk-based approvals across A2A action chains); Infosecurity Europe 2026 (London, 3-5 June 2026)
- Why NEXUS cares: Two adjacent governance signals in the same week. **(a) The OWASP Agentic Research Council** is the first *continuous* working group OWASP has chartered for the agentic threat class — the OWASP LLM Top 10 is a yearly list with a fixed list of items, but the new Agentic Research Council is chartered to *continuously* track the agentic CVE class (the same class NEXUS's `NexusOwaspClassDetector` from 2026-06-08-00 #1 is designed to defend against) and to publish pattern-class updates as new CVEs are disclosed. This is a NEXUS-relevant governance signal because the `NexusOwaspClassDetector` loads its pattern table from a versioned JSON file (`src/nexus_os/security/owasp_llm_patterns.json`) and the *canonical upstream body* for that pattern table is now the OWASP Agentic Research Council, not the yearly LLM Top 10. **(b) The Dark Reading HITL piece** is the first enterprise-press framing of *risk-based approvals across A2A action chains* as a distinct governance pattern, distinct from per-action audit, per-task credentials, and zero-trust agent auth (all of which NEXUS already has coverage for). The new pattern is the *chain-of-command* dimension: when an A2A delegation chain executes a high-impact action, HITL is required at the *delegation-chain* level, not at the *per-action* level, and the approval routing must follow the *chain*, not the *individual tool call*. This is a NEXUS-relevant governance pattern because the existing `nexus.kaiju.atx` module (from 2026-06-06-18 #2) tracks the delegation chain via the `issuerChain` field but does not currently route HITL approval requests through the chain. Three concrete NEXUS maps. **(a) OWASP Agentic Research Council ↔ NEXUS's `src/nexus_os/security/owasp_llm_patterns.json` and the existing `NexusOwaspClassDetector`** — the JSON file should add a top-level `upstream: "owasp-agentic-research-council"` field with a `feed_url` (e.g., `https://owasp.org/agentic-research-council/patterns.json`) and a `refresh_interval_hours: 6` field so the pattern table auto-refreshes from the OWASP council's feed (signed and versioned, mirroring the MCPSense v0.3.0 baseline-snapshot pattern from 2026-06-08-00 #2 with no auto-overwrite of the local snapshot). **(b) HITL A2A chain governance ↔ NEXUS's `src/nexus_os/governor/kaiju_auth.py` `KaijuAuthRequest.hold_queue` and the new `nexus.kaiju.atx` module** — the `KaijuAuthRequest.hold_queue` should add an `approval_routing_chain` field that lists the chain of WIMSE identities (each `wimse://agent/<spiffe_id>` with their role and approval-quorum weight) that must approve a high-impact A2A action, mirroring the Entra Agent OBO actor facet (`act`, `appid`, `xms_act`, `fct`, `idrel` claims) from 2026-06-08-00 #3 and the cross-org delegation chain from 2026-06-06-18 #2. **(c) Continuous-council update path ↔ NEXUS's `src/nexus_os/governor/proof_chain.py` and the VAP chain** — the VAP chain should add a `vap.owasp_pattern_table_refreshed{version, source=owasp_agentic_research_council, signed_by}` event that fires on every successful pattern-table refresh, so downstream jobs can audit which NEXUS host is running which version of the OWASP pattern table.
- Suggested follow-up: Add a `upstream: "owasp-agentic-research-council"` field to `src/nexus_os/security/owasp_llm_patterns.json` with a `feed_url: "https://owasp.org/agentic-research-council/patterns.json"` and a `refresh_interval_hours: 6` field; the `NexusOwaspClassDetector` polls the feed every 6 hours, validates the signature against the OWASP council's published JWKS, and merges new pattern classes into the local baseline-snapshot (no auto-overwrite, explicit `--update-baseline` UX, mirroring MCPSense v0.3.0 from 2026-06-08-00 #2). Add a `vap.owasp_pattern_table_refreshed{version, source, signed_by}` event to `src/nexus_os/governor/proof_chain.py` that fires on every successful pattern-table refresh. Extend `src/nexus_os/governor/kaiju_auth.py` `KaijuAuthRequest.hold_queue` with an `approval_routing_chain` field that lists the chain of WIMSE identities (each `wimse://agent/<spiffe_id>` with their role and approval-quorum weight) that must approve a high-impact A2A action, mirroring the Entra Agent OBO actor facet and the cross-org delegation chain from 2026-06-06-18 #2. Add a `risk_tier` enum (`low`, `medium`, `high`, `critical`) to `KaijuAuthRequest` that maps onto the HITL piece's "risk-based approvals" framing: `low` and `medium` skip the hold queue and rely on per-action audit; `high` and `critical` route the approval request through `approval_routing_chain` and require a quorum (e.g., 2-of-3 WIMSE identities from the chain must approve before the action is released). Add a `NexusA2AChainGovernance` module to `src/nexus_os/governor/` that, on every A2A delegation chain execution, walks the chain and emits a `nexus.a2a.chain_governance{action, chain_length, risk_tier, approval_required, quorum_state}` Loki event with the full chain of WIMSE identities and the approval state of each. Wire the new `NexusA2AChainGovernance` module into the Contain stage of `src/nexus_os/governor/trust_kernel.py` so a `risk_tier=high|critical` A2A action is auto-elevated to the Detect stage and held until the quorum is reached. Create `docs/governance/owasp-agentic-council-rubric.md` that maps each OWASP Agentic Research Council pattern class to the NEXUS primitive that defends against it (e.g., `flowise_stdio_chatflow` class → NEXUS `mcp/server.py` stdio kill-switch + `ChatflowWatchdog`; `dependency_prose` class → NEXUS `NexusDependencyProseScanner` from 2026-06-08-00 #2; `codex_auth` class → NEXUS `ConfigFileWatchdog` + `kaiju_auth.py` per-task credential primitive from 2026-06-07-18 #1) so a NEXUS-equipped deployment can produce a per-pattern-class coverage score. Add `tests/governance/test_owasp_pattern_table_refresh.py`, `tests/governance/test_a2a_chain_governance.py`, and `tests/governance/test_risk_tier_hold_queue.py` covering (a) successful pattern-table refresh from a signed OWASP feed, (b) refusal of an unsigned or out-of-date feed, (c) `risk_tier=low|medium` skipping the hold queue, (d) `risk_tier=high|critical` routing through `approval_routing_chain` and requiring quorum, (e) `NexusA2AChainGovernance` emitting the chain event with the full WIMSE identity chain and quorum state.
