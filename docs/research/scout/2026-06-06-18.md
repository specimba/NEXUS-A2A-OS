### 1. MCP 2026-07-28 RC + SEP-2575 Stateless/Sessionless — The First *Formal Spec Move* that Decouples MCP Identity from MCP Sessions, the First Time `protocolVersion + capabilities + identity + routing` Will Travel as a Per-Request `_meta` Envelope on Every `tools/call`, and the First Opportunity for NEXUS's `NexusGovernanceMCP` to Drop the `Mcp-Session-Id` Header Entirely and Become a Pure, Horizontally-Scalable, Stateless Front Door
- Source: byteiota https://byteiota.com/mcp-stateless-2026-release-candidate/ (2026-06); DEV Community https://dev.to/pueding/mcp-2026-07-28-rc-stateless-transport-4ma9; modelcontextprotocol/typescript-sdk PR #2231 https://github.com/modelcontextprotocol/typescript-sdk/pull/2231; PR #2227 conformance baseline; Issue #2842 SEP-2575 server-identity-in-_meta; modelcontextprotocol/typescript-sdk commit d618283 SSE keepalive for stateless; LocalCan https://www.localcan.com/blog/test-local-mcp-server-in-claude-ai (2026)
- Why NEXUS cares: SEP-2575 is the first *formal spec move* that decouples MCP identity from MCP sessions — every `tools/call` request now carries `protocolVersion`, `capabilities`, server/client identity, and tenant routing in a per-request `_meta` envelope; `initialize` and `Mcp-Session-Id` go away; stateless MCP servers can sit behind plain round-robin load balancers, no sticky sessions, no shared session store. Three concrete NEXUS maps. **(a) Stateless dispatch ↔ NEXUS's OpenClaw gateway on port 18789** — today NEXUS's MCP server assumes a single per-process `McpServer` instance with in-memory `Mcp-Session-Id` state; under SEP-2575 the TypeScript SDK (1.26+) requires `getServer()` to construct a **fresh `McpServer` per request** inside the HTTP entry point, otherwise concurrent stateless requests will leak responses between clients. NEXUS's `src/nexus_os/mcp/server.py` (NexusGovernanceMCP) and the OpenClaw gateway should adopt the same per-request factory pattern so that running multiple NexusGovernanceMCP instances behind a round-robin LB (e.g., the planned `nexus-modelrelay` pool from AGENTS.md) does not require sticky sessions. **(b) Per-request `_meta` envelope ↔ NEXUS's `trust_kernel.py` CDR-stage trust decision** — under SEP-2575 the protocol version, the client's declared capabilities, and the per-call identity all arrive on every request, not on `initialize`. This is the *exact* shape NEXUS's Contain→Detect→Respond state machine wants to see on every call: the Contain stage can read `ctx.mcpReq.protocolVersion` to apply version-gated policy (a server that doesn't speak the 2026 envelope gets the conservative policy), the Detect stage can read `ctx.client.capabilities` to know which MCP roots/sampling/logging the client claims, and the Respond stage can write a `nexus.envelope.received` Loki event with `(protocol_version, client_info_name, client_info_version, capabilities_fingerprint)` so a downstream monitoring job can spot a drifting client without re-parsing logs. **(c) Server identity in `_meta` (Issue #2842) ↔ NEXUS's `security/sanitizer.py` and the supply-chain-attestation follow-up from 2026-06-05-18 #1** — the open issue is that SEP-2575 makes `server/discover` optional, but server identity still needs to be carried in every server response's `_meta` for the same supply-chain reasons NEXUS's `compliance.py` `Supply Chain Verification` rule was extended to prompt templates + tool descriptions + MCP server manifests: a passive inventory tool must be able to bind a server's baseline to a *verifiable* identity, not a self-declared one. The recommended fix in the issue is exactly NEXUS-shaped: include `name`, `version`, and a signed `publisher` in every response's `_meta`; SEP-2809/ATSA attestation as the admission anchor. NEXUS can publish this as a `nexus.mcp.server_attestation` module that signs each NexusGovernanceMCP response with the deployment's `NEXUS_PUBLISHER_KEY` (a JWKS-published ed25519 key) and pins the deployment's `name`+`version` in the response, so a `nexus.mcp.drift_detector` job can compare the live `name`+`version` against a NEXUS-pinned snapshot and fire when the running deployment has been swapped under the same endpoint. The strategic cost-of-doing-nothing: if NEXUS does not adopt the SEP-2575 envelope shape, the AAIF/Linux-Foundation/MCP-coalition will define "compliant MCP server" without a NEXUS entry, and NEXUS's existing NexusGovernanceMCP will look like a 2025 fork.
- Suggested follow-up: Adopt the SEP-2575 per-request factory pattern in `src/nexus_os/mcp/server.py`: replace the module-scoped `McpServer` instance with a `def get_server() -> McpServer` factory, and call `get_server()` inside the `StreamableHTTPServerTransport` handler so every HTTP POST constructs a fresh server with the current `_meta` envelope. The factory reads `NEXUS_DEPLOYMENT_NAME`, `NEXUS_DEPLOYMENT_VERSION`, and the `NEXUS_PUBLISHER_JWKS_URL` env vars at request time and stamps them into the server's per-response `_meta` so passive inventory tools can verify the deployment. Wire the new server to read `ctx.mcpReq.protocolVersion` and `ctx.client.{capabilities,info}` on every request (mirroring TS-SDK PR #2231) and emit a `nexus.mcp.envelope` Loki event with `(protocol_version, client_name, client_version, capabilities_fingerprint, request_id)`. Add a `nexus.mcp.server_attestation` module that signs every NexusGovernanceMCP response with the deployment's ed25519 `NEXUS_PUBLISHER_KEY` and pins the deployment's `name`+`version`; the signature is included in the response `_meta` and a `nexus.mcp.drift_detector` daemon-side job compares the live `(name, version, signature)` against a NEXUS-pinned snapshot and fires when any field changes. Add a `nexus.mcp.stateless_lb` config doc that documents the round-robin-load-balancer-friendly deployment shape (no sticky sessions, no shared session store, every `Mcp-Session-Id` reference replaced with an explicit domain-specific `session_id` handle that the application maintains) and links from the AGENTS.md "OpenClaw" row. ### 2. OpenA2A AAP 0.2.0-Draft + ATX v1.1 (JCS RFC 8785) — The First Vendor-Neutral, IETF-Track Agent-Authorization Spec that Splits Identity from Authorization, the First Production Reference for a "Broker Resolves `grant://` to a Concrete Action, Agent Never Sees the Secret" Pattern, and a Direct Path for NEXUS's `kaiju_auth.py` to Emit the `KaijuAuthRequest` as a Signed `ATX` (Not Just a Dataclass) and to Add a `Credential Provider Interface` to `src/nexus_os/vault/memory_adapter.py`
- Source: opena2a-standards/agent-authorization-protocol https://github.com/opena2a-standards/agent-authorization-protocol (2026-06, 0.2.0-draft); opena2a-org/secretless-ai PR #77 https://github.com/opena2a-org/secretless-ai/pull/77 (ATX v1.1 JCS dual-support); DEV Community https://dev.to/chrishood/cross-organization-delegation-the-hardest-trust-problem-in-the-agent-economy-4bfa (AGTP+OAuth delegation chains, 551 Authority Chain Broken); DEV Community https://dev.to/kanywst/the-three-layers-of-ai-agent-authentication-what-id-jag-transaction-tokens-and-wif-actually-1mbk (ID-JAG → transaction tokens → WIF); Auth0 https://auth0.com/blog/why-ai-agents-need-their-own-permission-model/ (Token Vault + CIBA + RAR); Medium (Sourav Kumar, May 2026) https://medium.com/@sauravkumarsct/oauth-delegation-for-agents-o-b-o-1e75616c2033 (Entra Agent OBO actor facet)
- Why NEXUS cares: AAP 0.2.0 is the first vendor-neutral, IETF-track agent-authorization spec that *splits identity from authorization*: an agent's `ATX` (Agent Token eXchange) carries who the agent is, the issuer chain, the trust level, and the declared capabilities (e.g., `db:read`), but the *authorization* is determined by a local broker that evaluates broker policy against the ATX and resolves a `grant://resource` reference to a concrete action using one of three credential modes. The agent never sees the secret, never sees the backend address, and never sees the vendor name — exactly the "agent asks for intent, broker returns result" pattern the 2026-06-05-12 #1 OWASP L3 primitives require and that NEXUS's `KaijuAuthRequest` is one design refactor away from emitting. Three concrete NEXUS maps. **(a) `ATX` as the wire format for `KaijuAuthRequest` ↔ NEXUS's `src/nexus_os/governor/kaiju_auth.py`** — today `KaijuAuthRequest` is a Python dataclass that travels only inside the NEXUS process boundary. AAP 0.2.0 turns the same shape into a signed, JCS-canonicalized, JWS-wrapped token that can travel across organization boundaries, with a `signedCapabilities` field that a remote broker can verify offline. NEXUS should add a `nexus.kaiju.atx` module that serializes the existing `KaijuAuthRequest` as an `ATX v1.1` token (RFC 8785 JCS canonicalization, ed25519 signature, JWKS-published key under `NEXUS_ATX_JWKS_URL`), with the `capabilities` field lifted from the per-agent declared tool list and the `issuerChain` field listing the chain of `KaijuAuthRequest`s that authorized this one. The `requireSignedCapabilities` policy flag from ATX v1.1 (opena2a-org/secretless-ai PR #77) becomes NEXUS's `kaiju_auth.REQUIRE_SIGNED_CAPABILITIES=True` default, so a NEXUS broker refuses to resolve a `grant://` reference whose capabilities were declared in a forgeable v1.0 form. **(b) `Credential Provider Interface` ↔ NEXUS's `src/nexus_os/vault/memory_adapter.py` + the new `credential_vault` table** — the AAP spec defines a `Credential Provider Interface` (CPI) as the pluggable surface the broker calls to obtain a short-lived scoped credential (Retrieve / Assume / Exchange). NEXUS's `memory_adapter.py` already hashes + signs every entry on insert and consults the trust kernel on read; the extension is to add a `nexus.vault.credential_vault` table that stores *secret-bearing* entries (e.g., a backend's root API key) under the same trust-scored layer promotion, and expose a `nexus.vault.credential_provider` module that implements the CPI's three modes against the table: Retrieve returns the raw key to the broker (not the agent), Assume issues a short-lived role-scoped credential with a rotating signing key, and Exchange calls out to an external OAuth IdP for a token-exchange flow. The agent's `KaijuAuthRequest` becomes a `grant://` reference, the broker resolves it via the credential provider, and the agent only ever sees the *result* of the action — same as the OWASP L3 "agent never sees the secret" requirement. **(c) Cross-organization delegation chains with the 551 Authority Chain Broken return code ↔ NEXUS's `src/nexus_os/governor/trust_engine_v2.py` CDR stages** — the AGTP+OAuth pattern enforces that a delegation hop's scope is a strict subset of the prior hop's scope, returning 551 if violated. NEXUS's `trust_engine_v2.py` Contain stage should add the same invariant: every `KaijuAuthRequest.principal.scope` must be a subset of the parent `KaijuAuthRequest.principal.scope`, and a violation should fire `nexus.trust.scope_escalation` with a `return_code=scope_escalation` field. The Microsoft Entra Agent OBO actor facet (`act`, `appid`, `xms_act`, `fct`, `idrel` claims) is the production reference for the same dual-attribution shape: the downstream token carries both the user `sub` and the initiating agent `appid`, so an audit replay can answer "which human's authority, via which agent, was used to perform this action?" — NEXUS's existing `proof_chain.py` VAP chain can be extended with the same `(human_sub, agent_appid, parent_call_id)` triple per VAP event. The strategic cost-of-doing-nothing: if NEXUS does not adopt the AAP broker/resolution shape, the AAIF/Linux-Foundation/OpenA2A coalition will define "compliant agent authorization" without a NEXUS entry, and NEXUS's existing `kaiju_auth.py` will look like a 2025 fork.
- Suggested follow-up: Add a `nexus.kaiju.atx` module to `src/nexus_os/governor/kaiju_auth.py` that serializes the existing `KaijuAuthRequest` as an `ATX v1.1` token — RFC 8785 JCS canonicalization, ed25519 signature, JWKS-published key under `NEXUS_ATX_JWKS_URL`, with the `capabilities` field lifted from the per-agent declared tool list and the `issuerChain` field listing the chain of `KaijuAuthRequest`s that authorized this one. Set `REQUIRE_SIGNED_CAPABILITIES=True` as the default so a NEXUS broker refuses to resolve a `grant://` reference whose capabilities were declared in a forgeable v1.0 form, mirroring the ATX v1.1 policy flag from opena2a-org/secretless-ai PR #77. Add a `nexus.vault.credential_vault` table to `src/nexus_os/vault/memory_adapter.py` that stores secret-bearing entries (backend root API keys, OAuth client secrets) under the same trust-scored layer promotion as data entries, and expose a `nexus.vault.credential_provider` module that implements the AAP Credential Provider Interface's three modes (Retrieve / Assume / Exchange) against the table; the agent's `KaijuAuthRequest` becomes a `grant://resource` reference, the broker resolves it via the credential provider, and the agent only ever sees the result of the action. Extend `src/nexus_os/governor/trust_engine_v2.py` Contain stage with a `nexus.trust.scope_subset` check that fires `nexus.trust.scope_escalation` with `return_code=scope_escalation` when a `KaijuAuthRequest.principal.scope` is not a strict subset of the parent `KaijuAuthRequest.principal.scope` (the AGTP+OAuth 551 Authority Chain Broken pattern); the same check applies at every delegation hop. Extend `src/nexus_os/governor/proof_chain.py` VAP events with a `(human_sub, agent_appid, parent_call_id)` triple per event so a downstream audit can answer "which human's authority, via which agent, performed this action?" — the same dual-attribution shape the Microsoft Entra Agent OBO actor facet (`act`, `appid`, `xms_act`, `fct`, `idrel` claims) ships in production. Add `tests/governance/test_atx_broker.py` that constructs a synthetic agent with three tools, fires a `tools/call` whose `KaijuAuthRequest.scope` is `{read:users}`, fires a follow-up whose scope is `{read:users, write:users}` from the same parent, and asserts (a) the first call resolves and emits an ATX v1.1 token, (b) the second call fires `nexus.trust.scope_escalation` and is denied, (c) the credential provider's `Retrieve` mode never returns the raw API key to the agent (only to the broker), (d) the VAP chain records the `(human_sub, agent_appid, parent_call_id)` triple on every event. Add a `docs/spec/aap-0.2-compliance.md` page that maps every NEXUS governance primitive to the relevant AAP spec section (ATX wire format ↔ KaijuAuthRequest, Credential Provider Interface ↔ memory_adapter credential_vault, scope-subset invariant ↔ trust_engine_v2 Contain, actor facet ↔ proof_chain VAP triple) and notes the wire-format-version NEXUS will adopt on each AAP release.
