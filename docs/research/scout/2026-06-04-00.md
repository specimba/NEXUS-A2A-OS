### 1. Gemma 4 12B with Multi-Token Prediction — Mid-Weight Local SLM for Function Calling
- Source: https://arstechnica.com/google/2026/06/googles-new-gemma-4-open-ai-model-is-sized-for-your-laptop/
- Why NEXUS cares: Google released Gemma 4 12B as a mid-weight model that runs on a 16GB consumer laptop while preserving "complex multistep reasoning and agentic workflows" that previously required Gemma 4 26B MoE. Two architectural choices matter for NEXUS: (a) Multi-Token Prediction (MTP) drafters ship out-of-the-box, giving ~3× speculative-decoding speedup on idle cycles — directly relevant to NEXUS's `src/nexus_os/mcp/functiongemma_router.py`, which is the intent-classifier that runs on every MCP tool call; (b) the new single-matrix multimodal embedding (no separate vision/audio encoders) halves memory and reduces latency, which means a 12B-class SLM can plausibly run as the FunctionGemma Router on edge/NEXUS-OS deployments without the 26B VRAM profile. This is the first credible FunctionGemma-class local replacement that fits in consumer hardware.
- Suggested follow-up: Evaluate Gemma 4 12B as a drop-in for the FunctionGemma Router intent classifier in `src/nexus_os/mcp/functiongemma_router.py` — measure routing accuracy against the current classifier on the ModelRelay benchmark, and check whether the 16GB RAM profile lets the Router live on a dedicated sidecar instead of competing with the main agent for VRAM.

### 2. Priceline Penny Multi-Agent Architecture — Claude + OpenAI + Google Cloud Federated Stack
- Source: https://skift.com/2026/06/03/priceline-penny-revamp-multiagent-anthropic-claude/
- Why NEXUS cares: Priceline rebuilt its Penny assistant as a "squad of agents" combining Anthropic Claude (conversational reasoning), OpenAI models (search/voice), and Google Cloud (data + Gemini) inside one conversational interface. This is the highest-profile public production deployment of a heterogeneous multi-vendor agent stack to date. The architecture maps directly onto NEXUS's `src/nexus_os/engine/` (DAG routing across heterogeneous providers) and `src/nexus_os/gmr/` (intent-based model selection) — Penny demonstrates the market expectation that a "real" agentic assistant must orchestrate multiple models rather than rely on a single vendor. NEXUS's ModelRelay v6 already provides the routing primitive (NVIDIA NIM + Opencode + OpenRouter :free + Kilocode) but has no formal multi-agent composition layer; Penny is proof that the composition layer is now table stakes for production consumer agents.
- Suggested follow-up: Define a thin "agent squad" abstraction in `src/nexus_os/engine/` — a DAG node type that wraps a ModelRelay v6 call plus its own context-window, with explicit handoff semantics between sibling agents. This would let NEXUS orchestrate the same Claude + small-local-model + function-caller pattern that Priceline ships, while keeping ModelRelay as the underlying transport.

### 3. SafeBreach — Notification-Based Prompt Injection Against Google Gemini Voice Assistant
- Source: https://www.darkreading.com/application-security/malicious-notifications-could-trick-google-gemini-users
- Why NEXUS cares: SafeBreach disclosed a novel indirect-prompt-injection technique where attackers hide malicious instructions inside message notifications (in foreign languages or in muted hyperlinks) that Google Gemini's voice assistant then summarizes and silently executes as authorized interactions. The root cause is identical to the prior calendar-injection class: the assistant fails to convey the source of a summarized message, so attacker-controlled content inherits the trust level of the notification system. This is the same class of trust-boundary bypass NEXUS's `src/nexus_os/security/sanitizer.py` (prompt injection + ANSI escape filtering) and `src/nexus_os/governor/trust_kernel.py` (CDR-stage trust decisions) are designed to detect. The notification-channel vector is new: prior scout notes covered MCP-stdio, MCP-SSRF, OAuth CSRF, and Flowise stdio, but not the agent-assistant notification surface. NEXUS's `src/nexus_os/governor/compliance.py` policy rules should explicitly include "out-of-band channel (notification, calendar invite, email body) cannot authorize high-impact tool calls without re-authentication".
- Suggested follow-up: Add a notification-channel re-auth rule to `src/nexus_os/governor/compliance.py` — any tool call that originates from a summarized notification, calendar event, or other indirect-content channel must trigger a Kaiju Auth hold-queue review (`src/nexus_os/governor/kaiju_auth.py`) before execution, regardless of the source's apparent trust level. Pair with a sanitizer regex in `src/nexus_os/security/sanitizer.py` that flags any inbound tool-result channel marked as "summary" or "notification" for elevated scrutiny.
