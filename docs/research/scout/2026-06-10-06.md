### 1. CASCADE — Cascaded Hybrid Defense Architecture for Prompt-Injection Detection in MCP-Based Systems (zircote Friday Roundup Week 23, 2026-06-09; referenced arXiv paper) — The First Published Three-Tier Hybrid Defense (Regex/Entropy Prefilter → Embedding Semantic Analysis → Pattern Output Filtering) Quantified at 5,000-Sample Scale for MCP Tool-Description Poisoning, the First MCP Defense to Surface a Quantified 61.05% Recall Ceiling (39% of Injections Missed) That Validates NEXUS's Defense-in-Depth Mandate, and a Direct Path to Extend `src/nexus_os/security/sanitizer.py` With a `NexusToolDescriptionPoisoningDetector` That Adds Tool-Description Trust Scoring and Pairs With the Existing `NexusOwaspClassDetector` From 2026-06-08-00 #1
- Source: zircote "Friday Roundup — Week 23: The Spec Becomes the Substrate" https://zircote.com/blog/2026/06/friday-roundup-week-23/ (June 9, 2026); CASCADE paper: "CASCADE: A Cascaded Hybrid Defense Architecture for Prompt Injection Detection in MCP-Based Systems" (arXiv, 2026; cited in the roundup); companion piece "MCP Threat Modeling and Tool Poisoning" (also cited in the roundup)
- Why NEXUS cares: CASCADE is the first *quantified*, *publicly-evaluated* three-tier hybrid defense specifically for MCP tool-description poisoning, and the reported numbers (precision 95.85%, false-positive rate 6.06%, recall only 61.05% on a 5,000-sample evaluation) are the cleanest empirical argument yet that *no single tier* is sufficient and that NEXUS's existing defense-in-depth mandate is structurally correct. The architecture. **(a) Tier 1 — fast regex + entropy prefilter** — looks for known injection patterns (e.g., "ignore previous instructions", "you are now", "respond only with", "disregard the above") and high-entropy strings (compressed/obfuscated payloads); cheap, runs at line rate, catches the obvious cases. **(b) Tier 2 — semantic analysis with embeddings** — uses an embedding model to compute the semantic distance between each tool description's *intent* (what the description says the tool does) and any embedded *instruction* (what the description tells the agent to do); flags descriptions where the instruction drifts from the intent. **(c) Tier 3 — pattern-based output filtering** — watches the agent's emitted tool calls and refuses any call whose arguments encode instructions (a tool that fetches a URL whose path contains "respond only with" is blocked) or whose argument shape does not match the tool's declared JSON-Schema. The 61.05% recall ceiling — roughly 2 in 5 injections slip past all three tiers — is the canonical result that argues for a *fourth* tier: per-tool trust scoring plus runtime policy enforcement (the architectural shape of NEXUS's own `NexusTokenRotationGapDetector` and `NexusLLMGatewayAuthBypass` patterns from 2026-06-09-12). Three concrete NEXUS maps. **(i) `NexusToolDescriptionPoisoningDetector` in `src/nexus_os/security/sanitizer.py`** — on every MCP tool-registration call (the `tools/list` and `tools/register` paths in the NexusGovernanceMCP at `src/nexus_os/mcp/server.py`), run the CASCADE tier-1/2/3 stack as a *pre-registration gate*; if all three tiers agree the description is clean, register the tool with `trust_score=high`; if tiers 2+3 agree but tier 1 fires, register with `trust_score=medium` and emit `nexus.mcp.tool_desc_poison_suspected{tool_name, tier, score, severity=medium|high|critical}` to Loki; if any tier fires *and* the description's intent-embedding distance exceeds the 0.62 quantile (the empirically reported threshold from the CASCADE evaluation), refuse registration with a 403 and emit a `critical` event. **(ii) `src/nexus_os/security/owasp_llm_patterns.json` extension** — add a `mcp_tool_description_injection_indirect` class signature per the pattern from 2026-06-08-00 #1: `(layer=tool_description) AND (semantic_drift(intent, instruction) > 0.62) AND (entropy(description) > 4.5) AND (description_length > 256) AND (matches_injection_pattern_count >= 1)`; wire into the existing `NexusOwaspClassDetector` so a match emits `nexus.owasp.llm01_class_detected{class=mcp_tool_description_injection,source=cascade_tier_2}`. **(iii) `src/nexus_os/security/cascade_eval_manifest.json`** — seed NEXUS with the 5,000-sample CASCADE evaluation set (or its public subset) as a regression test for the `NexusToolDescriptionPoisoningDetector`; the 61.05% recall ceiling is the floor NEXUS must beat, and a 90%+ recall target is achievable by combining CASCADE with NEXUS's existing `NexusTokenRotationGapDetector` + the `KaijuTaskCredential` per-task scoping from 2026-06-07-18 #3 (the architectural pattern that limits the *consequence* of the 39% miss rate, even when the detection itself fails).
- Suggested follow-up: Add a `NexusToolDescriptionPoisoningDetector` to `src/nexus_os/security/sanitizer.py` that implements the CASCADE three-tier stack as a pre-registration gate for every tool in `src/nexus_os/mcp/server.py` (the NexusGovernanceMCP); emit `nexus.mcp.tool_desc_poison_suspected{tool_name,tier,score,severity}` Loki events and refuse registration on critical findings. Add a `mcp_tool_description_injection_indirect` class signature to `src/nexus_os/security/owasp_llm_patterns.json` per 2026-06-08-00 #1: `(layer=tool_description) AND (semantic_drift(intent,instruction) > 0.62) AND (entropy(description) > 4.5) AND (description_length > 256) AND (matches_injection_pattern_count >= 1)` — wire into the existing `NexusOwaspClassDetector` so a match emits `nexus.owasp.llm01_class_detected{class=mcp_tool_description_injection,source=cascade_tier_2}`. Seed `src/nexus_os/security/cascade_eval_manifest.json` with the public CASCADE 5,000-sample evaluation set as a regression target for the new detector, with a floor of 61.05% recall (CASCADE's published ceiling) and a stretch goal of 90%+ recall when combined with `KaijuTaskCredential` scoping from 2026-06-07-18 #3. ### 2. Topaz — Explainable Model Routing for Agentic Workflows (arXiv:2604.03527, referenced via Lynkr dev.to, 2026-06-09) — The First Paper to Explicitly Locate Explainable Routing at the *Gateway* Layer (Not the Agent Layer) With Skill-Based Model Profiles, the First Published Framework to Treat Routing Decisions as Auditable, Replayable, Overridable Artifacts, and a Direct Path to Add a `NexusRoutingDecision` Audit Record to `src/nexus_os/engine/gmr_router.py` and a Skill-Based Model Profile Table to `ModelRelay` at `localhost:8040`
- Source: DEV Community "Why Explainable Model Routing Belongs at the Gateway Layer" https://dev.to/lynkr/explainable-llm-routing-is-the-missing-layer-in-agentic-systems-and-why-it-matters-for-lynkr-12ph (June 9, 2026); paper: "Explainable Model Routing for Agentic Workflows" (arXiv:2604.03527); Lynkr is the production reference for the Topaz framework
- Why NEXUS cares: Topaz is the first paper to make the architectural argument that *explainable* model routing belongs at the *gateway* layer, not the agent layer, and the argument maps cleanly onto NEXUS's `ModelRelay v6` at `localhost:8040` (per AGENTS.md) and the GMR router at `src/nexus_os/engine/gmr_router.py` (per 01_PROJECT_STATE.md). The paper's three contributions each close a specific NEXUS gap. **(a) Skill-based model profiles** — instead of routing on opaque heuristics (latency, cost, model name), Topaz profiles every model by *capability* (logic, code generation, tool use, factual knowledge, writing quality, instruction following, summarization) and the routing decision is a *vector match* between the prompt's inferred required capabilities and the model profile's capability scores. NEXUS's `ModelRelay` already classifies intent into {code, reasoning, research, fast, security, general} (per AGENTS.md), but the *capability profile* of each upstream model is not yet published; a `model_capability_profile.json` in `src/nexus_os/engine/` would let the GMR router pick the best-fit model for a *specific* prompt, not just for a *class* of prompts. **(b) Explicit cost-quality optimization** — Topaz treats the routing decision as a constrained optimization (minimize cost subject to quality >= threshold, or maximize quality subject to cost <= ceiling) with the constraints and the solution *visible* to the operator; NEXUS's `src/nexus_os/monitoring/token_policy.py` enforces the budget side, but the *quality* side is implicit (the tier floor of 65 is a heuristic, not a measured guarantee). **(c) Developer-facing explanations** — every Topaz routing decision emits a plain-language explanation ("routed to model X because the prompt scored 0.8 on code generation and 0.6 on tool use, model X has profile {0.9, 0.8} on those skills, and model Y is $0.0003 cheaper but scores {0.7, 0.5}") that can be audited, replayed, and overridden. NEXUS's existing ModelRelay Loki events (`nexus.relay.route{provider,model,intent,tier,latency_ms,cost_estimate}`) capture the *inputs* but not the *reasoning*; a `NexusRoutingDecision` audit record that adds the *why* (capability vector, constraint set, alternatives considered, override flag) would make ModelRelay v6 the *first* zero-cost relay with explainable routing, a meaningful differentiator. Three concrete NEXUS maps. **(i) `src/nexus_os/engine/model_capability_profile.json`** — seed with the published 27-model roster from ModelRelay v6 (per AGENTS.md: 5 NVIDIA NIM, 3 Opencode, 22 OpenRouter, 1 Kilocode) and a per-model skill vector `{logic, code, tool_use, factual, writing, instruction_following, summarization}` with scores 0.0–1.0; the GMR router reads this on every request and uses the prompt's inferred skill vector to pick the best fit. **(ii) `NexusRoutingDecision` audit record in `src/nexus_os/engine/gmr_router.py`** — on every ModelRelay routing decision, emit `nexus.relay.routing_decision{request_id, prompt_skill_vector, candidate_models, chosen_model, chosen_skill_match, alternative_considered, cost_estimate, quality_estimate, override_flag, reasoning_text}` to Loki; the `reasoning_text` is the Topaz-style plain-language explanation; the `override_flag` is set when an operator manually pins a model. **(iii) Replay-and-override endpoint on the ModelRelay HTTP server** — add `GET /v1/chat/replay/{request_id}` (returns the full `NexusRoutingDecision` for replay), `POST /v1/chat/override` (operator pins a model for a class of prompts), and `GET /v1/chat/routing-stats` (returns the distribution of chosen models, average skill-match score, override rate); these three endpoints turn ModelRelay from a black-box router into an auditable, replayable routing plane and make the GMR router's decisions *operator-visible* for the first time.
- Suggested follow-up: Add `src/nexus_os/engine/model_capability_profile.json` seeded with the 27-model ModelRelay v6 roster, each with a 7-skill vector `{logic, code, tool_use, factual, writing, instruction_following, summarization}` (scores 0.0–1.0); update `src/nexus_os/engine/gmr_router.py` to read the profile and pick the best-fit model on a *prompt skill vector* match, not just on the existing intent-class tier. Add a `NexusRoutingDecision` audit record to the GMR router that emits `nexus.relay.routing_decision{request_id, prompt_skill_vector, chosen_model, skill_match, alternative_considered, cost_estimate, quality_estimate, override_flag, reasoning_text}` to Loki; the `reasoning_text` is the Topaz-style plain-language explanation. Add three ModelRelay HTTP endpoints — `GET /v1/chat/replay/{request_id}` (full `NexusRoutingDecision` for replay), `POST /v1/chat/override` (operator pins a model for a class of prompts), `GET /v1/chat/routing-stats` (distribution + override rate) — so ModelRelay v6 becomes the first zero-cost relay with explainable, auditable, replayable, overridable routing; this is the structural differentiator versus every other free-tier LLM relay.

### 3. Aegis-Layer — Deterministic MCP Sidecar With Ed25519 Identity-Bound Capability Tokens + Strict JSON-Schema Policy Engine (dev.to/yash_aegis, 2026-06-09) — The First Published MCP Defense That Replaces Probabilistic Guardrails With a Stateless, Edge-Sidecar, Cryptographically-Bound, Sub-2ms Verification Layer, the First MCP Defense to Drop Requests on Ed25519 Signature Failure (Not on Heuristic Score), and a Direct Path to Add a `NexusMCPCapabilityToken` Issued by `src/nexus_os/mcp/server.py` and Verified by a New `NexusMCPSidecar` Process on the Same Host as the ModelRelay
- Source: DEV Community "Why Probabilistic Guardrails Fail Autonomous AI Agents (And How We Built a Deterministic Fix)" https://dev.to/yash_aegis/why-probabilistic-guardrails-fail-autonomous-ai-agents-and-how-we-built-a-deterministic-fix-4hjm (June 9, 2026); Aegis-Layer is the production reference implementation
- Why NEXUS cares: Aegis-Layer is the first published MCP defense to *replace* probabilistic guardrails (CASCADE-style regex + embeddings + output filtering) with a *deterministic* edge-sidecar that uses Ed25519 cryptographic identity binding + a strict JSON-Schema policy engine, and the design is the structural opposite of the 2026 finding #1 above. Where CASCADE aims to *detect* prompt injection in tool descriptions with 61.05% recall, Aegis-Layer aims to *prevent* the attack class entirely by refusing any request whose signature is invalid or whose JSON-RPC payload deviates from the registered tool's schema by even a single character. The architecture. **(a) Ed25519 Identity-Bound Capability Tokens (IBCTs)** — every request to the MCP server carries an Ed25519 signature over the canonicalized JSON-RPC payload; the signature is bound to (i) the agent's public key (registered at agent boot), (ii) the tool name (so a token for `read_file` cannot be replayed as `write_file`), and (iii) a per-request nonce (so a token cannot be replayed across requests). Verification is O(1) and runs in under 2ms on commodity hardware; failed signatures are dropped at the edge with no further processing. **(b) Dynamic JSON-Schema Policy Engine** — every registered tool has a strictly defined JSON-Schema (parameter types, value constraints, allowed string patterns); the sidecar rejects any request whose arguments do not match the registered schema, *including* a request whose arguments match the schema in *type* but deviate in *value* (e.g., a `path` argument that is a string but contains a path-traversal payload is rejected because the schema specifies `pattern: "^[a-zA-Z0-9_/-]+$"`). **(c) Stateless zero-latency verification** — the sidecar is a lightweight Docker process positioned before the MCP server; it holds no per-request state beyond the nonce cache (which is in-memory and rotates every 60s), so a single sidecar process can scale to thousands of requests per second on a 1-vCPU container. The 2ms p99 verification latency is the key operational metric: probabilistic guardrails add 50–200ms per request (embedding model + classifier), which is enough to make a *chat* response feel sluggish; deterministic verification is invisible. Three concrete NEXUS maps. **(i) `NexusMCPCapabilityToken` issued by `src/nexus_os/mcp/server.py`** — on agent boot, the NexusGovernanceMCP issues a per-agent Ed25519 keypair (or accepts a public key registered via `nexus.mcp.agent_register`) and signs a `NexusMCPCapabilityToken` for each tool the agent is allowed to call; the token carries `(agent_pubkey, tool_name, scope, ttl, nonce)` and is bound to the agent's identity. **(ii) `NexusMCPSidecar` process** — a small Bun process (mirroring the Aegis-Layer Docker sidecar) that sits between every ModelRelay LLM call and the NexusGovernanceMCP, verifying the Ed25519 signature on every request, checking the JSON-Schema on every argument, and dropping failed requests with a `nexus.mcp.sidecar_drop{reason=signature|schema|nonce|expired,tool,agent,severity=high|critical}` Loki event; the sidecar is stateless and adds <2ms p99 to the request latency, preserving the chat UX. **(iii) `KaijuAuth` integration** — the existing `src/nexus_os/governor/kaiju_auth.py` is the natural place to issue the per-agent keypair and scope the per-tool capability; a `NexusMCPCapabilityToken` is the per-MCP-call analog of the per-task `KaijuTaskCredential` from 2026-06-07-18 #3, and the two should share the same cryptographic substrate (Ed25519) so a NEXUS deployment has *one* identity primitive, not two.
- Suggested follow-up: Add a `NexusMCPCapabilityToken` to `src/nexus_os/mcp/server.py` that issues a per-agent Ed25519 keypair on `nexus.mcp.agent_register` and signs a scoped token per tool call (the token carries `(agent_pubkey, tool_name, scope, ttl, nonce)`); the issuance lives in `src/nexus_os/governor/kaiju_auth.py` so the `KaijuTaskCredential` (per-task, 2026-06-07-18 #3) and the `NexusMCPCapabilityToken` (per-MCP-call) share the same Ed25519 substrate. Add a `NexusMCPSidecar` Bun process that sits between ModelRelay and the NexusGovernanceMCP, verifies the Ed25519 signature on every request, checks the JSON-Schema on every argument, and drops failed requests with `nexus.mcp.sidecar_drop{reason,tool,agent,severity}` Loki events; stateless, <2ms p99, scales to thousands of RPS on 1 vCPU. Add a `NexusMCPSchemaRegistry` to `src/nexus_os/security/` that holds the canonical JSON-Schema for every registered tool (parameter types, value constraints, allowed string patterns) and is read by the sidecar on every request; tool-registration events from the NexusGovernanceMCP auto-update the registry, and a `nexus.mcp.schema_drift{tool,field,expected,actual,severity}` Loki event is emitted when a tool's runtime arguments deviate from the registered schema (the Aegis-Layer signature behavior). Document the Aegis-Layer deterministic-sub-2ms design as the recommended deployment shape for any NEXUS MCP server, and add a `nexus.mcp.sidecar_required=true` flag to the NexusGovernanceMCP `tools/list` response so downstream agents know to attach a `NexusMCPCapabilityToken` to every request.
