### 1. A2A Protocol v1.2 — Cryptographic Agent Cards and Production Governance
- Source: https://dev.to/om_shree_0709/google-io-2026-mcp-is-now-infrastructure-spark-managed-agents-webmcp-more-4ap0
- Why NEXUS cares: A2A v1.2 introduces cryptographic agent cards for domain verification and is governed by the Linux Foundation's Agentic AI Foundation, with 150 organizations in production (Microsoft, AWS, Salesforce, SAP, ServiceNow). NEXUS's `src/nexus_os/mcp/server.py` (NexusGovernanceMCP) exposes tools but has no agent-card identity layer. The cryptographic verification pattern from A2A v1.2 maps onto `src/nexus_os/governor/trust_kernel.py` (CDR-stage trust decisions) and `src/nexus_os/governor/proof_chain.py` (VAP chain, tamper detection). The cross-org governance model (Linux Foundation) also mirrors how NEXUS handles multi-repo trust across the NEXUS mesh.
- Suggested follow-up: Investigate adopting A2A v1.2 as an additional protocol layer alongside MCP for agent-to-agent coordination across the NEXUS mesh repos. Cross-reference agent-card schema with the TrustKernel identity model.

### 2. WebMCP — Open Web Standard for Browser-Based Agent Function Calling
- Source: https://dev.to/om_shree_0709/google-io-2026-mcp-is-now-infrastructure-spark-managed-agents-webmcp-more-4ap0
- Why NEXUS cares: WebMCP exposes structured tools (JavaScript functions, HTML forms) as an open standard so browser-based AI agents can call them directly. Chrome origin trial starts in Chrome 149; Gemini support in Chrome is forthcoming. NEXUS's `src/nexus_os/bridge/` and `src/nexus_os/relay/` handle protocol translation and API ingress; WebMCP is a complementary ingress path for browser-contextual tool calls. The OpenClaw gateway (`gateway + control-ui`) could benefit from a WebMCP integration to expose browser-accessible tools directly to agent flows.
- Suggested follow-up: Map WebMCP tool schemas against `src/nexus_os/bridge/` to identify where browser-based tool calls could route into the NEXUS bridge layer. Watch only for now — WebMCP is still in origin trial.

### 3. Multi-Model Majority Voting for Hallucination Detection
- Source: https://medicalxpress.com/news/2026-05-ai-vote-medical-hallucinations-chatbot.html
- Why NEXUS cares: A Binghamton University team tested seven open-source LLMs using RAG across 10,000 medical prompts and introduced a cross-model majority-voting protocol — requiring each model to reference an authoritative database then voting on results — achieving 100% consistency on supported answers and eliminating unmatched hallucinations. The protocol maps onto NEXUS's `src/nexus_os/governor/trust_kernel.py` (CDR-stage trust decisions) and `src/nexus_os/governor/trust_engine_v2.py` (Contain→Detect→Respond state machine): the voting mechanism is a concrete implementation of the "Detect" stage in the trust engine. It also complements the TokenPolicy + TokenGuard pipeline in `src/nexus_os/monitoring/`.
- Suggested follow-up: Consider a multi-model voting guard in `src/nexus_os/monitoring/token_guard.py` — hard fails when models disagree below a majority threshold, similar to the RAG-grounded majority vote approach. This would add a hallucination-detection layer to the existing token consumption guard.
