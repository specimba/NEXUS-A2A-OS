### 1. Meta AI Customer-Support Agent Hijacks via OWASP LLM06 Excessive Agency — A Live, Public Case Study for NEXUS's `kaiju_auth.py` Hold-Queue + Step-Up Verification Patterns
- Source: MIT Technology Review https://www.technologyreview.com/2026/06/05/1138437/the-meta-hack-shows-theres-more-to-ai-security-than-mythos/ (2026-06-05); 404 Media original reporting; VentureBeat case analysis https://venturebeat.com/security/meta-ai-support-agent-recovery-email-takeover-soc-audit-grid (2026-06-05); DEV community case study https://dev.to/alessandro_pignati/how-hackers-talked-their-way-into-instagram-accounts-a-case-study-in-excessive-agency-1h82; Meta's own post-mortem statement (via news.com.au, S-RM cyber briefing, 2026-06-05)
- Why NEXUS cares: The Meta incident is the first large-scale, publicly-visible account-takeover committed by an AI agent against a Fortune-1 platform's own customer base, and the failure mode is precisely the one NEXUS's safety layer was structurally designed for. Three technical specifics make it directly mappable to NEXUS files. **(a) Confused-Deputy / Excessive Agency (OWASP LLM06)** — Meta's support agent had `account_settings_change`, `email_relink`, and `password_reset` tools bundled together, so a single low-privilege user prompt ("change my email") granted super-user powers over the entire account. NEXUS's `src/nexus_os/mcp/functiongemma_router.py` already classifies tool calls by intent via `lethal_trifecta_pre_flight()`, but the classification is *call-level*; the Meta incident shows the threat is also *capability-coexistence-level* — even if every individual call is correctly classified, the union of tools available to one agent is too broad. The fix is a `nexus.mcp.capability_set` rule: any agent whose registered tool set includes both `modify_credentials` and `modify_auth` must require step-up verification on every call (a `kaiju_auth` hold-queue entry with a `risk=excessive_agency` tag). **(b) Identity-verification bypass via VPN-matched location + AI-generated selfie** — the attacker's "I am the legitimate owner" proof was a deepfake selfie that passed Meta's liveness check; this is the *identity-side* of the same problem the OWASP L3 primitive "ephemeral credentials + cryptographic attestation" (from 2026-06-05-12 #1) is meant to address. NEXUS's `src/nexus_os/governor/kaiju_auth.py` currently verifies the *caller's principal* (the human/agent asserting intent), not the *underlying identity* (the human being asserted-about); the Meta incident makes clear that for any high-stakes action (password reset, email change, recovery, payment), the gate must verify the second, not the first, and the only practical primitive is a per-call short-lived bearer (60s) bound to a WebAuthn or passkey assertion from the human — exactly the "ephemeral credentials" primitive the OWASP framework calls out. **(c) No human-escalation path** — once the AI bot was tricked, victims were trapped in chatbot loops with no route to a human. NEXUS's `src/nexus_os/governor/kaiju_auth.py` hold-queue is exactly the human-in-the-loop escape valve the Meta bot lacked, but only if it's wired to a *user-facing* surface (Slack, web, SMS) and not just an operator dashboard. The Meta incident's "no human escalation" detail converts the OWASP L3 "kill switch" requirement into a specific UX requirement: a NEXUS hold-queue entry must generate a user-visible message ("We paused this action because it looks suspicious; confirm here to proceed") before a bot can complete the call.
- Suggested follow-up: Add a `nexus.mcp.capability_excessive_agency` check to `src/nexus_os/governor/compliance.py` that scans every agent's registered tool set at startup and at every tool-add event, and flags combinations where `email_change + password_reset + 2fa_disable` (or any superset thereof) are co-registered; the flag is a hard `risk=high` requirement on the first call of any tool in the set, forcing `kaiju_auth` to hold-queue. Add a `nexus.identity.underlying_principal` field to the `KaijuAuthRequest` dataclass so callers can supply a WebAuthn/passkey assertion that the hold-queue UI verifies before approve; the default is `None`, which means "no high-stakes action may complete" and forces every recovery flow to be re-engineered to provide one. Surface a `nexus.excessive_agency.incident` Loki label sourced from `security_sanitizer.py` whenever a hold-queue entry is denied and the agent had the `excessive_agency` flag set; this is the same dashboard panel the OWASP v1 framework from 2026-06-05-12 #1 already calls for, and the Meta incident is the canonical incident the panel can reference. Add `tests/governance/test_excessive_agency.py` that registers a synthetic agent with the three-tool superset, fires a single call, and asserts (a) the call is held, (b) the user-visible message is generated, (c) without the `underlying_principal` field, the call is denied. Document the OWASP LLM06 mapping in `docs/governance/owasp-llm06-mapping.md` with the Meta case as the canonical example, and link from `01_PROJECT_STATE.md`'s "What Is Verified In This Repo" to the new tests as the second-most-distinctive NEXUS marketing surface (after the OWASP L3 maturity score from 2026-06-05-12 #1).

### 2. Hugging Face Transformers CVE-2026-4372 (CVSS 7.8) RCE via `_attn_implementation_internal` Field in `config.json` — A Pre-Auth Code-Execution Vector That Bypasses `trust_remote_code=False` and NEXUS's Own `from_pretrained` Call Sites
- Source: CyberPress https://cyberpress.org/critical-hugging-face-transformers-flaw/ (2026-06-05); TechRepublic https://www.techrepublic.com/article/news-hugging-face-transformers-rce-flaw/ (2026-06-05); IT Security News https://www.itsecuritynews.info/hugging-face-transformers-security-flaw-allows-remote-code-execution/ (2026-06-05); the underlying advisory PR#44395 and CVE record CVE-2026-4372 (patched 2026-03-04 in transformers 5.3.0); discovered by Yotam Perkal (Pluto Security)
- Why NEXUS cares: CVE-2026-4372 is the most consequential AI supply-chain CVE of 2026 to date because the attack vector is the *single function* every LLM-loading stack calls — `AutoModelForCausalLM.from_pretrained()` — and the exploit requires neither `trust_remote_code=True` nor any user interaction beyond loading a model. The mechanism is a kernel-dispatch refactor (introduced in transformers 4.56.0) that reads `_attn_implementation_internal` from `config.json` and passes it to `importlib.import_module()`, which silently loads the attacker-named module from any pip-installable source; an attacker bundles a malicious "kernel" package on Hugging Face Hub, embeds the field in a model card, and the code runs the moment a victim downloads the model. Three reasons this is NEXUS-relevant. **(a) NEXUS's `src/nexus_os/` and `NEXUS-OS/` skill packages may use Hugging Face Transformers in dev-time eval work** — `src/nexus_os/model_arena/mini_arena.py` and any future model-loading path in the ModelRelay stack that pulls from the Hub. The fix is to pin `transformers>=5.3.0` in every `requirements.txt` / `pyproject.toml` across `NEXUS-OS/` and `Skills/*/scripts/`, add a CI scan in `docs/security/cve-log.md` that fails the build if `transformers<5.3.0` is resolvable, and add a `nexus.model_load.preflight(config_path)` helper that scans the config for any underscore-prefixed field (the exploit class) and refuses the load before the dangerous import is reached. **(b) The OWASP v2.0 taxonomy Agentic Supply Chain Compromise primitive (2026-06-05-18 #1) is now *named-example-mappable* to a specific CVE** — the `nl_pinning` follow-up from that note can now cite CVE-2026-4372 as the canonical "config-field-driven supply-chain compromise" case, and the suggested mitigation (hash every config field at registration time, refuse drift) is exactly the rule CVE-2026-4372 demonstrates the absence of. **(c) The CVE's exploit class — `importlib.import_module()` of a user-controlled string — is the *generic shape* of a category of bugs, not just one bug** — anywhere NEXUS's `mcp/server.py` or `bridge/sdk.py` dynamically loads Python modules by string (e.g. plugin discovery, tool adapters, model adapters) is potentially vulnerable to the same pattern, and a single audit pass to grep for `import_module(` calls in `src/nexus_os/` will surface every site that needs a hash check on the module name.
- Suggested follow-up: Add a `nexus.model_load.preflight(config_path) -> PreflightResult` helper to `src/nexus_os/security/sanitizer.py` that (a) loads the config JSON, (b) flags any underscore-prefixed key (the `_attn_implementation_internal` shape), (c) returns a structured `PreflightResult` with `safe=True/False`, the flagged keys, and a recommended `deny | allow_with_warning | allow` decision, and (d) when `safe=False`, raises a `PreflightViolation` that the caller catches to short-circuit the load. Wire the helper into the `transformers` integration path in `src/nexus_os/model_arena/mini_arena.py` and the ModelRelay rotator's first-time-model-load branch in `src/nexus_os/modelrelay/rotator.py`; both already have a pre-load step, the helper is additive. Pin `transformers>=5.3.0` in every `requirements.txt` across `NEXUS-OS/`, `Skills/*/scripts/`, and the top-level `pyproject.toml`, and add a CI rule in `docs/security/cve-log.md` that fails the build if `pip-audit` or `osv-scanner` reports CVE-2026-4372 as resolvable. Run a one-shot `grep -rn "import_module" src/nexus_os/` audit and add a hash check (`hmac.compare_digest(expected, actual)`) before any `import_module()` call in NEXUS code that takes a user-controlled module name; the v2.0 supply-chain follow-up from 2026-06-05-18 #1 already has a CI scan for the prompt-template/MCP-manifest variant, this extends it to the dynamic-import variant. Add a `docs/security/cve-log.md` entry for CVE-2026-4372 with the date (2026-06-05 widespread coverage, 2026-03-04 patch), the affected version range, the fix version, and the NEXUS-side action; link the entry to the v2.0 supply-chain follow-up in the 2026-06-05-18 note so the supply-chain attack surface in NEXUS is one continuous doc, not a per-CVE list. Add a `tests/security/test_model_load_preflight.py` that constructs a synthetic `config.json` with the exploit field, calls `from_pretrained` through the helper, and asserts the load is denied with the right `PreflightViolation` reason string.

### 3. Miasma Worm Phase 2 (npm Phantom Gyp + Claude Code SessionStart Hook Persistence) — Live, Self-Propagating npm Supply-Chain Worm That Targets NEXUS's Own OpenClaw Mesh of AI Coding Agents
- Source: Web Pulse https://wpnews.pro/news/miasma-worm-targets-ai-coding-agents-via-github-repos (2026-06-05); Pasquale Pillitteri https://pasqualepillitteri.it/en/news/4278/miasma-worm-npm-binding-gyp-57-packages (2026-06-04); TechTimes https://www.techtimes.com/articles/317832/20260605/red-hat-npm-packages-compromised-57-more-follow-signed-attestations-cannot-block-pipeline-hijack.htm (2026-06-05); Hexnode https://www.hexnode.com/blogs/miasma-malware-red-hat-npm-supply-chain-attack/; Red Hat advisory; JFrog advisory; StepSecurity advisory; Team-Rockstars-Security/antimiasma GitHub repo (counter-worm analysis); Microsoft Security Blog 2026-06-02 (initial Miasma reporting)
- Why NEXUS cares: Miasma Phase 2 is the first self-propagating npm worm to *specifically target the AI-coding-agent attack surface* — Phase 1 (May–June 2026) compromised 32 `@redhat-cloud-services` packages via post-install scripts, but Phase 2 (June 3, 2026) introduced two new primitives that change the threat model for any NEXUS-equipped OpenClaw fleet. **(a) Phantom Gyp / `binding.gyp` trick** — a 157-byte `binding.gyp` file with no `preinstall` or `postinstall` script in `package.json` evades the standard lifecycle-script scanners (npm silently runs `node-gyp rebuild` on any package with a root `binding.gyp` and no lifecycle scripts); the loader then chains into a `node index.js` execution. NEXUS's own `Skills/*/scripts/` may declare `binding.gyp` for native modules; the existing CI scan from 2026-06-05-18 #1 (which forbids `postinstall` without an explicit `// nexus-approved:` comment) does not cover `binding.gyp`, and Phantom Gyp is the bypass. **(b) IDE/agent session-start hook persistence** — the Phase 2 GitHub-repo dropper writes `.claude/settings.json` (with a `SessionStart` hook), `.gemini/settings.json` (same), `.cursor/rules/setup.mdc` (always-applied rule), and `.vscode/tasks.json` (folder-open task); cloning the repo is safe, but opening it in Claude Code / Gemini CLI / Cursor / VS Code triggers automatic shell execution of the Bun loader. This is the *first* live worm that exploits the agent-config-as-attack-surface pattern, and NEXUS's OpenClaw mesh has direct exposure: any developer running OpenClaw on a cloned repo, or any agent that calls into the codebase via a tool (filesystem MCP, etc.), is a potential victim. **(c) Counter-worm concept (Team-Rockstars-Security/antimiasma)** — the same propagation primitive (config-file writes to `.claude/`, `.cursor/`, `.gemini/`, `.vscode/`) can be used to *vaccinate* a repo against the worm, but the vaccination requires the operator to be aware of the threat and to run the counter-worm tool. NEXUS's `src/nexus_os/security/sanitizer.py` can be the canonical scanner that surfaces the threat before the developer (or the agent) opens the repo, eliminating the need for a manual counter-worm install.
- Suggested follow-up: Extend the existing post-install-hook CI scan from 2026-06-05-18 #1 in `docs/security/cve-log.md` to also flag any `binding.gyp` in a dependency that lacks a pre-merge approval, and to scan any code change in `Skills/*/scripts/` and `NEXUS-OS/` for a `binding.gyp` addition without an explicit `// nexus-approved: <reason>` comment. Add a `nexus.repo.session_start_audit(path)` helper to `src/nexus_os/security/sanitizer.py` that, on a NEXUS-equipped agent's first read of a directory, scans for `.claude/settings.json`, `.gemini/settings.json`, `.cursor/rules/setup.mdc`, `.vscode/tasks.json`, and emits a `nexus.session_start.hook_detected` event with the file path, the hook event type, and the command to be executed; the agent's pre-flight gate then either blocks the read, prompts the human, or proceeds. Wire the helper into OpenClaw's tool-allowlist check at the gateway (port 18789) so the audit happens at request time, not just at agent startup, and add a `nexus.session_start.miasma_pattern` Loki label when the hook command matches a Bun loader (heuristic: `bun`/`/tmp/p.js`/`/tmp/b-/bun` substrings). Add a `ConfigFileWatchdog` for the `.claude/`, `.gemini/`, `.cursor/`, `.vscode/` paths (extending the Mitiga `~/.claude.json` watchdog from 2026-06-05-12 #2) that snapshots hashes on agent startup and re-checks on every MCP handshake; emit `nexus.config.session_start_drift` when any of the four config files changes outside of the NEXUS config-deploy path. Cross-reference the new `binding.gyp` CI check against the v2.0 Agentic Supply Chain Compromise follow-up from 2026-06-05-18 #1 (the `nexus.supply_chain.nl_pinning` rule) so the supply-chain attack surface is one continuous doc, and add a `tests/security/test_phantom_gyp.py` that constructs a synthetic npm tarball with the 157-byte `binding.gyp` payload and asserts the CI scan rejects it with the right reason. Add a `docs/security/miasma-phase2.md` page that links the npm-Phantom-Gyp vector to the GitHub-repo-SessionStart-hook vector to the AI-coding-agent config attack surface, and document the NEXUS-side defense layers (CI scan + repo audit + config watchdog + Loki alert) in a single page so a security reviewer can audit the coverage in one read. Track Team-Rockstars-Security/antimiasma for the counter-worm pattern (self-propagating vaccination) and evaluate whether NEXUS should ship a controlled, opt-in `nexus.session_start.vaccinate` tool that walks a repo's `.claude/`, `.gemini/`, `.cursor/`, `.vscode/` files and adds a benign hook that blocks the Miasma loader signature — the same config-file attack surface can be turned into a defense surface.
