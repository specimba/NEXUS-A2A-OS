### 1. Anthropic LLM ATT&CK Navigator — Real-World AI Cyber Operations Mapped to MITRE ATT&CK
- Source: https://red.anthropic.com/2026/attack-navigator/
- Why NEXUS cares: Anthropic published a long-form analysis (in partnership with Verizon for the 2026 DBIR) mapping AI-enabled cyber operations to the MITRE ATT&CK framework. Headline stat: the share of medium- or high-risk actors using AI for cyber operations grew ~1.7× in under a year, from 33% to 56% between the first and second halves of their study window. This is the first publicly released, ATT&CK-tagged taxonomy of LLM-as-attacker behavior tied to real banned accounts — a directly consumable threat-modeling input. It maps onto NEXUS's `src/nexus_os/security/sanitizer.py` (prompt injection + ANSI escape filtering) and the policy-engine rules in `src/nexus_os/governor/compliance.py`: each ATT&CK technique ID becomes a policy rule ID, and each observed attack pattern becomes a unit test. The Navigator also validates NEXUS's bet on CDR-stage trust decisions in `src/nexus_os/governor/trust_kernel.py` — the same containment/detection/response loop shows up as a recurring pattern across multiple AI-driven actor profiles.
- Suggested follow-up: Ingest the ATT&CK Navigator's technique list as a YAML/JSON file in `docs/threat-model/` and wire a CI check that every ATT&CK technique flagged "AI-observed" has at least one corresponding policy rule in `src/nexus_os/governor/compliance.py` or sanitizer regex in `src/nexus_os/security/sanitizer.py`; missing coverage should fail the test baseline (currently 634 passed).

### 2. Self-Replicating AI Worm (Papernot et al., U Toronto / Vector / Cambridge)
- Source: https://gizmodo.com/a-fundamentally-new-threat-researchers-develop-new-ai-powered-worm-that-might-be-unstoppable-2000766975
- Why NEXUS cares: A research team (Papernot + Vector Institute + Cambridge) demonstrated a self-replicating worm that carries a small open-weight LLM as its reasoning engine, generates tailored attack strategies per target, and propagated through an isolated 33-host network spanning Linux, Windows, and IoT devices. This is a fundamentally new threat class: the worm's payload is itself an LLM agent, so traditional signature/AV defenses are blind to it. For NEXUS this lands in two places: (a) `src/nexus_os/governor/kaiju_auth.py` — impact/intent auth must be extended to recognize "agent that spawns sub-agents" as a distinct high-impact class, because the byo-LLM worm pattern is exactly "sub-agent = new identity," and Kaiju's current hold-queue model assumes the requesting identity is the one acting; (b) `src/nexus_os/governor/proof_chain.py` — VAP chain events need a "sub-agent spawn" primitive so a parent chain can attest each child agent's identity, scope, and teardown; without this, containment can't survive a worm that creates a new agent identity per hop. The paper also shows the worm succeeded against "common corporate network vulnerabilities" (e.g., reused passwords) — a class NEXUS's `src/nexus_os/vault/memory_adapter.py` cannot detect but should flag if it observes the same actor identity in two distinct network zones within a short window.
- Suggested follow-up: Add a `subagent_spawn` event type to `src/nexus_os/governor/proof_chain.py`; require every child agent to inherit a parent VAP segment and a scoped sub-policy from `compliance.py`. Add a "multi-zone actor" anomaly to `src/nexus_os/vault/memory_adapter.py` that raises trust-score decay when a single memory-layer entry is read from two distinct network zones within a configurable window.

### 3. Adversa AI Risk Quadrant — Only 11 of 100 Tested Agents Are "Capable Well-Defended"
- Source: https://www.securityweek.com/security-of-100-ai-agents-tested-and-ranked-what-you-need-to-know/amp/
- Why NEXUS cares: Adversa evaluated 100 commercial AI agents across 10 categories and only 11 landed in the "capable well-defended" quadrant. The report's central structural finding: "the same vendors shipping the most capable agents ship the widest attack surface — a structural feature of the market, not a handful of outliers." This is the first systematic public benchmark that ties capability and defense into a single quadrant, and it directly motivates NEXUS's `src/nexus_os/model_arena/mini_arena.py` (report-only evidence collection) plus the safety layer in `src/nexus_os/security/sanitizer.py`. Specifically, Adversa's three evaluation axes (vulnerability, impact, defense strength) are a near-perfect match for NEXUS's three-axis trust model: vulnerability → sanitizer detection rate, impact → Kaiju Auth impact classification, defense strength → compliance.py rule coverage. Running NEXUS's own NexusGovernanceMCP (`src/nexus_os/mcp/server.py`) and FunctionGemma Router (`src/nexus_os/mcp/functiongemma_router.py`) through Adversa's methodology would generate a public-facing capability+defense quadrant NEXUS could publish.
- Suggested follow-up: Add a `model_arena/adversa_quadrant.py` report-only evaluator that scores NEXUS components (NexusGovernanceMCP, FunctionGemma Router, TrustKernel) on the three Adversa axes and emits a quadrant placement; run it in CI so any future regression in any axis moves NEXUS to a worse quadrant and is visible in the test baseline.

### 4. Coralogix $200M Series F — AI-Native Observability with Built-in Agent and MCP/CLI Interfaces
- Source: https://www.securityweek.com/coralogix-raises-200m-at-1-6b-valuation-to-scale-ai-observability-platform/
- Why NEXUS cares: Coralogix raised $200M at a $1.6B valuation specifically to scale its AI-native observability platform, which unifies logs/metrics/traces/security and ships with a built-in AI agent (called "Olly") plus MCP and CLI interfaces for "human engineers and AI systems to investigate incidents, automate operations, and reason over production data in real time." The 11-month gap from a $115M Series E to a $200M Series F is itself a signal: investor thesis is that observability for AI agents is the next infra category. More than half of Coralogix's enterprise customers now use Olly or their own AI models for incident investigation, which is the production pattern NEXUS should anticipate for its own agent deployments. For NEXUS this validates the Loki integration (`http://localhost:3100`) already in the infra map, and points at three concrete next steps: (a) `src/nexus_os/observability/` should expose its own MCP server (e.g., `GET /api/observability/query`) so external agents like Olly or a customer-deployed NEXUS agent can query NEXUS audit logs without going through Slack or the dashboard; (b) `src/nexus_os/monitoring/token_guard.py` and `src/nexus_os/observability/audit_log.py` should emit Loki-tagged events with stable labels (agent_id, cdr_stage, proof_chain_id) so Loki queries can reproduce a full incident timeline; (c) the multi-agent incident-investigation pattern (agent reads logs, queries, suggests remediations, and gets human-in-the-loop approval before action) is a direct validation of NEXUS's `src/nexus_os/governor/kaiju_auth.py` hold-queue model.
- Suggested follow-up: Add an MCP-exposed observability route in `src/nexus_os/mcp/server.py` (e.g., `mcp_tool: nexus.observability.query` accepting a Loki LogQL query and returning structured results) so external agents can consume NEXUS audit events with a structured contract. Add a Loki label-schema doc at `docs/observability/loki-labels.md` enumerating the stable label set so the schema is greppable and reviewable.
