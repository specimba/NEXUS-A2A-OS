### 1. Devenex Execution Control Plane — Four-Artifact Decision-to-Execution Lineage, EU AI Act / SOC 2 / ISO 42001-Aligned
- Source: https://www.digitaljournal.com/article/devenex-launches-the-execution-control-plane-for-enterprise-ai/ (2026-06-03/04 launch at Google Cloud Next 2026); cross-confirmed https://www.techtimes.com/articles/317674/20260603/ai-agents-are-executing-across-enterprise-systems-devenex-was-built-govern-them-before-they-act.htm and https://www.truenorthradionetwork.com/online_features/press_releases/as-ai-agents-scale-enterprises-demand-execution-control-devenex-takes-control/article_b7b3c775-a9fd-51d2-a7b4-2e9999ad12f2.html
- Why NEXUS cares: Devenex is the first vendor to put a name and an artifact model on a pattern NEXUS already has in skeleton form, and it ships with a concrete compliance-mapping that NEXUS does not yet advertise. The Devenex design is a *pre-execution* control plane that emits four sequential artifacts per agent action — (1) **Canonical Plan** (the parsed intent + tool arguments), (2) **Authorization Record** (the policy decision + approver chain), (3) **Execution Trace** (the side-effect timeline), (4) **Evidence Pack** (the immutable, signed bundle of 1–3) — and markets this lineage as audit-grade proof against EU AI Act Art. 12 / 14, SOC 2 CC7.2, and ISO 42001. NEXUS already has all four primitives but in different files: `src/nexus_os/governor/trust_kernel.py` produces the CDR-stage trust decision (close to the Authorization Record), `src/nexus_os/governor/proof_chain.py` emits the VAP chain (close to the Evidence Pack), `src/nexus_os/observability/audit_log.py` records the Execution Trace, and `src/nexus_os/mcp/functiongemma_router.py` produces the Canonical Plan via the lethal-trifecta pre-flight from the 2026-06-05-00 note. What NEXUS is missing is the *single* lineage object that bundles all four into a tamper-evident record keyed on a (plan_id, auth_id, trace_id, evidence_id) tuple and surfaces a `nexus.governance.lineage.get` query for compliance reviewers. The Devenex launch is also a market signal: the "Execution Control Plane" segment is splitting out of "AI Observability" as its own category (per the Mneme HQ analysis cited below), and NEXUS's safety consolidation from 2026-05-18 is already aligned with that segment — but the marketing surface is owned by Devenex and Microsoft, not NEXUS.
- Suggested follow-up: Add a `GovernanceLineage` dataclass to `src/nexus_os/governor/proof_chain.py` that binds `(plan_id, authz_id, trace_id, evidence_id)` as a single 4-tuple and exposes `get_lineage(plan_id) -> LineageBundle` for the dashboard. Wire the FunctionGemma router in `src/nexus_os/mcp/functiongemma_router.py` to emit a `plan.canonicalized` event that becomes the tuple head; wire the Kaiju hold-queue decision in `src/nexus_os/governor/kaiju_auth.py` to emit the `authz.recorded` event as the second element; audit_log emits `trace.executed`; proof_chain signs the bundle as `evidence.sealed`. Add a Loki label `nexus.governance.lineage.{plan,authz,trace,evidence}.id` and a `nexus.governance.lineage.broken` alert that fires when any of the four IDs is missing from the bundle (the Devenex "broken lineage = audit failure" rule). Add a doc page `docs/governance/lineage.md` mapping each artifact to its compliance framework (EU AI Act Art. 12/14, SOC 2 CC7.2, ISO 42001) so the NEXUS dashboard can advertise compliance parity with the Devenex marketing claim.

### 2. Microsoft Agent Control Specification (ACS) + Execution Containers (MXC) SDK — Open-Source Interception Standard with Composable Sandboxes
- Source: https://techcrunch.com/2026/06/02/microsoft-offers-devs-a-better-way-to-control-ai-agent-behavior/ (ACS spec, open-source, plug-ins for LangChain + OpenAI/Anth/SF SDKs); https://blogs.windows.com/windowsdeveloper/2026/06/02/windows-platform-security-for-ai-agents/ (MXC SDK, composable sandbox with Entra/Intune push via Agent 365)
- Why NEXUS cares: Microsoft shipped two pieces in one news cycle that map cleanly onto NEXUS's `src/nexus_os/mcp/functiongemma_router.py` and `src/nexus_os/governor/`. **ACS** is a single-file, portable policy spec that defines four interception points in the agent loop — `before_input`, `before_tool_use`, `after_tool_result`, `before_final_response` — and the four standard actions (`allow`, `redact`, `human_intervention`, `block`). The interception points are the same set NEXUS's FunctionGemma router already calls ("pre-flight" before tool use, post-call sanitization, hold-queue approval) but ACS gives them a stable naming convention and a JSON policy file format. NEXUS could adopt ACS as a *declarative* surface for the trust_kernel CDR stages: the existing `Contain` stage maps to `before_input`, `Detect` to `before_tool_use` and `after_tool_result`, and `Respond` to `before_final_response`. The Microsoft plug-ins for LangChain and the OpenAI/Anth SDKs also means a NEXUS operator who runs an SDK-wrapped agent can drop in the ACS policy file unchanged and get the same interception coverage as NEXUS's Python governance layer. **MXC** is the runtime counterpart: a composable sandbox abstraction (gVisor-style for I/O-heavy agents, Kata for untrusted code) that the Agent 365 / Intune stack can push to specific agents. This is essentially the `src/nexus_os/security/` containment primitive NEXUS has been writing as Python decorators, but lifted to the OS level — and with Intune pushing the policy, the sandbox state is enumerable from the same place that enumerates the agent fleet. The risk is that if NEXUS does not adopt the ACS interception vocabulary, the cross-platform open-source standard will define the term and NEXUS's FunctionGemma router will read as a fork.
- Suggested follow-up: Add an ACS-style policy loader to `src/nexus_os/mcp/functiongemma_router.py` that accepts a JSON file matching the ACS interception-point schema and translates it to the existing NEXUS CDR-stage hook set: `before_input` → `trust_kernel.contain()`, `before_tool_use` → `lethal_trifecta_pre_flight()` (from 2026-06-05-00 finding #3), `after_tool_result` → `sanitizer.post_call()`, `before_final_response` → `compliance.final_gate()`. The four ACS actions map onto existing NEXUS actions: `allow` → pass-through, `redact` → `security_sanitizer.redact()`, `human_intervention` → `kaiju_auth.hold_queue()`, `block` → `kaiju_auth.deny()`. Document the mapping in `docs/governance/acs-mapping.md` and add a regression test `tests/governance/test_acs_bridge.py` that loads a sample ACS policy file and asserts the NEXUS CDR stages fire in the right order. For MXC: add a `nexus.sandbox.composable` flag to `src/nexus_os/security/sanitizer.py` that signals the Python process is running inside an MXC sandbox and short-circuits the in-Python containment decorators (no double-wrapping), and add a Loki label `nexus.sandbox.runtime={python|none|mxc}` so the dashboard can show the distribution.

### 3. Cerbos Externalized Authorization Pattern for AI Agents — Tools as Resources, Agents as Principals, Fail-Closed
- Source: https://www.cerbos.dev/blog/authorization-for-ai-agents-what-to-build-before-eu-ai-act-deadline (2026-06-04); cross-confirmed by the same pattern in https://www.checkpoint.com/blog/ai-defense-plane/ and the Mneme HQ "AI Agent Governance Is Splitting Into Two Markets" analysis at https://mnemehq.com/insights/ai-agent-governance-two-markets/
- Why NEXUS cares: The Cerbos post is the most concrete, written-down version of a pattern NEXUS has only half-implemented: the policy decision (PDP) and policy enforcement (PEP) for AI agents should be **externalized** from the agent's reasoning loop, with three load-bearing properties. (a) **Tools are resources, agents are principals** — a tool call is `(principal=agent, action=invoke, resource=tool, context=arguments, attributes=trust_score)`, evaluated by a PDP before execution. This is exactly the model NEXUS's `src/nexus_os/governor/kaiju_auth.py` uses with `impact_class` and `intent`, but today the policy evaluation happens inside the same Python process as the agent — which means a compromised agent process can short-circuit the decision. (b) **Fail-closed if PDP unreachable** — if the policy engine times out or returns 5xx, the call is denied, not allowed. NEXUS today has no such guard: a stuck KaijuAuth thread silently allows the call. (c) **Auditable trail of owner / purpose / decision per leaf tool call** — to satisfy EU AI Act Art. 86 (right to explanation of automated decisions). NEXUS has VAP chains in `src/nexus_os/governor/proof_chain.py` but the chain is per-proposal, not per-tool-call — the granularity is wrong for Art. 86. The Mneme HQ framing is also useful: governance is splitting into "runtime" (the control plane that sits in the request path) and "architectural" (the system integrity over time). NEXUS's `governor/` package is the runtime half; the `vault/` and `db/` packages are the architectural half. The blog post gives NEXUS a vocabulary to describe that split.
- Suggested follow-up: Refactor `src/nexus_os/governor/kaiju_auth.py` so the policy decision is callable over HTTP from a sibling process (or from a sidecar), with the `evaluate(principal, action, resource, context, attributes) -> Decision` signature mirroring the Cerbos post. The default in-process call stays for latency, but a `NEXUS_KAIJU_REMOTE_URL` env var switches to the remote PDP. Add a fail-closed timeout in `src/nexus_os/bridge/sdk.py` (e.g. 200ms) that calls `kaiju_auth.deny()` on timeout and emits a `nexus.kaiju.fail_closed` event to the VAP chain in `src/nexus_os/governor/proof_chain.py`. Add a `kaiju_auth_record` per-tool-call event type (new in proof_chain) that captures `(owner_agent_id, purpose, decision, policy_version, evaluated_at, evaluator_host)` and add a `nexus.kaiju.tool_decisions` Loki label with `decision={allow|deny|hold|fail_closed}`. Document the change in `docs/governance/externalized-pdp.md` and add a test `tests/governance/test_fail_closed.py` that points the in-process Kaiju at a black-hole address and asserts every call returns deny + emits a `fail_closed` event. This is the smallest change that turns NEXUS's `governor/` from a library call into a runtime control plane, in the sense the Mneme HQ post describes.

### 4. JFrog 2026 Self-Hosted AI Survey — 68% Australia Self-Hosts, 47% Block Unapproved IDE/MCP, 18% Have Zero MCP Governance
- Source: https://securitybrief.com.au/story/australia-leads-in-self-hosted-ai-use-jfrog-finds (2026-06-04); cross-confirmed https://ecommercenews.com.au/story/australia-leads-in-self-hosted-ai-use-jfrog-finds; the 18%-no-governance number from https://www.sipoch.com/en/article/300330020889947
- Why NEXUS cares: JFrog's 2026 research gives NEXUS three concrete baselines that are useful to size monitoring and gating. (a) **68% of Australian orgs self-host AI** (highest globally) — NEXUS's `src/nexus_os/relay/model_relay.py` already runs in self-hosted mode, so the self-hosted share is the *addressable* user base for a self-hosted governance layer like NEXUS. (b) **47% of orgs use automated controls to block unapproved IDE extensions and MCP servers** — this is the floor rate for automated block. NEXUS's `src/nexus_os/security/sanitizer.py` should be benchmarked against this: if a NEXUS-equipped fleet's auto-block rate is below 47%, the governance surface is not catching what the average self-hosted org catches. (c) **18% of orgs have no active governance for IDE extensions and MCP servers** and **23% of developers treat AI-suggested fixes as virtually final** — both are risks the NEXUS safety layer was designed to mitigate, but the second (developer over-trust) is the harder one: a CI scan catches a bad PR, but it does not catch a developer who merges the AI's suggested fix without review. The 23% figure is also a useful baseline for `src/nexus_os/model_arena/mini_arena.py` if it adds a "developer-overtrust" eval: the eval should reproduce the 23% number on the current SOTA model and then measure NEXUS-prompted responses. JFrog also published an MCP Server gateway reference (https://jfrog.com/learn/ai-security/ai-gateway/) that lists the same four production-readiness items (auth, rate limit, audit, health) the initeagent post covered — useful as a checklist but not a new primitive.
- Suggested follow-up: Add a `nexus.governance.coverage_rate` metric to `src/nexus_os/observability/audit_log.py` that counts, per agent/lane, what fraction of tool calls were gated by `src/nexus_os/governor/kaiju_auth.py` (the denominator) vs. auto-allowed (the numerator, should be zero in steady state). Surface the coverage rate on the NEXUS dashboard and alert when the auto-allow rate exceeds 1% (well below the JFrog 47% baseline, but the alert catches regressions). Add a `nexus.security.mcp_unapproved` counter that fires when `src/nexus_os/security/sanitizer.py` rejects a tool call from an MCP server that is not on the approved list — this maps directly onto the JFrog "47% block unapproved MCP" baseline and lets NEXUS publish its own block rate as a marketing-grade signal. Add a Loki dashboard panel `JFrog benchmark` that shows NEXUS's block rate vs. the JFrog 47% and the 18%-no-governance floor. For the 23%-developer-overtrust figure: add a "developer trust" eval to `src/nexus_os/model_arena/mini_arena.py` that runs a battery of NEXUS-prompted model responses on the same set of AI-suggested-fix scenarios and reports the model's tendency to assert the fix is correct without evidence; the eval should reproduce the 23% baseline on the unprompted model.
